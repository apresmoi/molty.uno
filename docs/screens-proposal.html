Molty Screens

How a skill draws on Molty. Proposal, nothing built. 2026-11-22.

Recommendation: write screens in SVG, with holes. Each screen is a folder: the drawing (screen.svg), a script that works out what goes in the holes (screen.mjs), and notes for the agent (screen.md). The build turns the SVG into the same package Molty installs today, so the device needs no change to start. With one page of docs, outside models wrote valid SVG screens 14 times in 18, and valid Molty YAML 0 times in 9 (3 after we fixed its guide). The script-returns-SVG form tied, but needs new firmware and loses on-device taps.

Key choices

  • One folder per screen; a one-screen skill is just SKILL.md plus screen.svg.
  • The drawing is plain SVG in a small Molty profile, plus {{ holes }}, repeats and conditions.
  • The script does all the maths; the drawing never computes anything.
  • A hole takes any SVG value; our library turns it into Molty's numbers before sending.
  • Taps go by element id; a tap can read words or open another screen with no agent in the loop.
  • Motion is declared, never animated: same id moves, new gathers from dust, gone dissolves.
  • One checker that says what to fix in plain words; the laptop preview is the device's own renderer.
  • Astrology moves over by a converter, accepted only when its package comes out byte for byte the same.

Open decisions

  1. Retire the YAML screen language once astrology has moved? Recommend yes.
  2. File names: screen.svg / screen.mjs / screen.md, or yours (display.svg / script.mjs / reference.md)? Recommend screen.*.
  3. Where SVG values become Molty numbers: our agent-side library, the relay, or the firmware? Recommend the library.
  4. Also offer "send a finished SVG now", with no package, for one-off drawings? Recommend later, not now.
  5. When does motion by id get its firmware? Recommend right after the migration.

screen.mjs

Plain JavaScript that runs beside the agent, never on Molty. It must export feed; it may export tools (what the agent can do with this screen) and example (sample arguments the build uses to check and preview). It uses one small class from our npm package.

import { Screen } from '@molty/screens';
import { sky } from '../../lib/sky.mjs';

export default new Screen({
  example: { date: '2026-11-01' },
  // the values the holes read: everything computed here
  feed({ date }) {
    const s = sky(date);
    return { bodies: s.bodies.map(placeBody), aspects: s.tightest(3).map(line), signs: s.signs.map(signTap) };
  },
  // what the agent can do with this screen; each becomes a command it can run
  tools: {
    show: { about: 'The chart for a date.', args: { date: 'YYYY-MM-DD, default today' } },        // the default: feed, then send
    read: { about: 'Read one planet aloud while it is lit.', args: { body: 'sun, moon, ...' },
            run: (molty, { body }) => molty.light(body) },
  },
});

The agent runs any screen's tool the same way: npx molty-screens molty-astro chart show --date 2026-11-01. The library pairs with the molty skill, sends the values, waits for taps and prints SAY: and FACTS: lines as the astro script does today. A skill's own command-line script shrinks to the parts that are really about its subject.

screen.md (per-screen notes for the agent)

---
about: All ten bodies on the zodiac wheel, joined by their tightest aspects.
---
Show it when they ask for "my chart" or "the whole sky". Say one line, then stop: the wheel holds 60 s.
A tap on a planet reads it on Molty; a tap on a sign opens its close-up on Molty for its reading's length.
You get the tap event ({"spot":"leo","opened":"sign-closeup"}): don't talk over a close-up.

SKILL.md links each screen.md where it says when to use it, so the agent loads a screen's notes only when it is about to use that screen. The build appends to each the screen's values and a ready call, as build/display.md does today.

c. the script returns SVG

About 50 lines, all in one function. Molty gets the whole drawing every time.

export function render(sky) {
  const out = [];
  const at = (deg, r) => {
    const t = (180 + deg) * Math.PI / 180;
    return [r * Math.cos(t), -r * Math.sin(t)];
  };
  out.push(`<circle id="rim" r="90" fill="none"
    stroke="ink" stroke-width="1.2"/>`);
  out.push(`<circle id="inner" r="75" ... />`);
  out.push(`<line id="borders" x1="75" x2="90"
    ... data-around="12"/>`);
  SIGNS.forEach((s, i) => {
    const [x, y] = at(15 + 30 * i, 82.5);
    out.push(`<use id="${s}" href="#${s}"
      x="${x - 5.3}" y="${y - 5.3}" width="10.6"
      height="10.6" color="${COLOR[i % 3]}"/>`);
    // the sign's block, a tap that opens its
    // close-up: but the close-up's values must
    // travel in the drawing too, for all 12 signs
    out.push(blockTap(s, i, sky));
  });
  for (const a of sky.tightest(3)) {
    const [x1, y1] = at(a.from.lon, a.from.r);
    const [x2, y2] = at(a.to.lon, a.to.r);
    out.push(`<line id="${a.id}" x1="${x1}" ...
      data-reads="${esc(a.reading)}"/>`);
    out.push(litRings(a));
  }
  for (const b of place(sky.bodies)) {
    const [x, y] = at(b.lon, b.r);
    out.push(`<use id="${b.name}" href="#g-${b.name}"
      x="${x - 6}" y="${y - 6}" width="12"
      height="12" color="${COLOR_OF[b.name]}"
      data-tap-r="8" data-reads="${esc(b.reading)}"/>`);
  }
  return `<svg xmlns="http://www.w3.org/2000/svg"
    viewBox="-100 -100 200 200"
    data-duration="hold">${out.join('')}</svg>`;
}

3. What a screen may contain

The glass

Always viewBox="-100 -100 200 200": the centre is 0,0, x grows right and y grows down, as in any SVG, and the round glass is the circle of radius 100 (412 pixels across, so 1 unit is about 2 pixels). rotate() is SVG's: degrees, clockwise. Anything past the rim is an error, not clipped.

Later elements paint on top. Colors are Molty's names (ink, grid, dim, white, erase), the skill's own tokens, or #rrggbb.

Holes, repeats, conditions

  • {{ name }} or {{ item.field }} fills a whole attribute or a whole text, or one number inside rotate() or translate(). Never part of a sum or a sentence: the script sends the finished value.
  • A hole may hold anything SVG accepts there, even a whole d or transform; the library turns it into Molty's numbers before sending. Every model in the test sent arc paths and coordinates this way, so we make it work instead of forbidding it.
  • data-each="b in bodies" repeats an element per list element, from the script or from a fixed table in display.yaml.
  • data-if="{{ running }}" draws an element only when the value is true. (The test showed the need: models invented three different hacks for it.) On the device it becomes a list of none or one, which Molty already handles.

Taps

  • An element with an id and data-reads is a tap target. A tap shows the words at once, word by word, and the agent gets {"spot": id}.
  • Its own shape is where to tap: a circle's disc, a line's band, a symbol's box, an arc's band (as wide as its stroke). data-tap-r widens it. With stroke="none" and fill="none" it is an invisible tap area.
  • data-opens="sign-closeup" opens another screen on Molty with no agent in the loop. It takes its values by name from the tapped list element, then from this screen. data-seconds says how long.
  • class puts an element in a group; data-lights="a b" lights those groups; data-lit shows an element only while lit; data-grow says how much the lit drawing grows.

Motion

  • Between two sends of a screen, or between two screens: an element whose id is in both moves and changes in place; a new one gathers from dust; a gone one dissolves. The author only names; Molty decides the how and the timing.
  • Inside a screen: data-from and data-until (seconds) for timed reveals, as today. data-until="0" is refused, not read as "forever".
  • Until the firmware for motion lands, every change is today's dust swap; screens written now gain motion later without edits.

The wire map

The build compiles each element to one of today's items and records, for each hole, how to get Molty's number from the script's SVG value: divide by 100, flip y, turn a clockwise angle into Molty's counter-clockwise one, a dash percent into an arc's end, a path's endpoints into its centre and angles. The library applies the map before sending. A field used two ways is sent twice under two names, by the build, so the author never meets the rule.

Preview

molty-display preview loads the built package into the firmware's own web module (the same C code, compiled for the browser, as on the /demo/ page) and plays a screen with the values feed returns for its example. You see the dust, the taps and the opened close-ups exactly as the glass draws them. A plain SVG viewer still shows the drawing, but skips anything colored with a token name such as ink; the build also writes a copy with tokens turned into hex for that.

5. The experiment: what outside models wrote

One page of docs for each of three forms (today's YAML, SVG with holes, a script that returns SVG), same length and care, and the same three tasks: the natal chart (ten bodies, three aspects, twelve signs, taps and a close-up) and two screens never seen in this repo, a kitchen timer with a progress ring and a weather card with a three-day row. Authors: Codex (medium effort), Grok and a fresh Claude, each through our harness with the docs and the task inline, no repo access. Gemini (agy) was dropped: its preflight failed (not logged in), so it never ran. 12 runs in all, every one complete.

Judges that cannot be argued with: for YAML, the real build tool, then the device's own binding and reference renderer; for SVG, a checker that enforces the page's rules, then a headless browser picture. What each got wrong

  • YAML: declaring inputs, not drawing, sank it. Round 1: all three wrote list fields in a short form. Grok and Claude put a comma or a colon inside an unquoted sentence, which YAML reads as a new key. Round 2: Codex and Grok gave every list field an example (only inputs take one); Claude's sign tap lacked words and a radius, reported one at a time. Grok's timer leaves a dot at 12 o'clock at zero.
  • SVG with holes: Codex and Grok put the three-day row past the rim. All three computed every position in the script (none used rotate()) and sent whole arc paths as values. With no condition form, each invented one: lists of none or one, or data-until="0", which today's device reads as "forever". Invisible tap areas were not described, so they painted black shapes under the drawing.
  • Script returns SVG: Claude and Grok invented attributes to hand the sign to the close-up a tap opens: in this form Molty holds no values to pass on. Codex painted its sign tap areas.

What it means

  • Models write correct SVG far more often than correct Molty YAML: 14 of 18 against 0 of 9, and 3 of 9 even after fixing the guide.
  • SVG with holes and the script form tie on correctness; the device side decides between them (section 2).
  • Every SVG failure was caught by the checker with a plain message. The profile above already takes in the four fixes the test asked for: conditions, invisible tap areas, holes that take any SVG value, and how an opened screen gets its values.
  • Small sample: three authors, three tasks, one page each. It shows a direction, not a precise rate.
6. Migration: astrology, with identical output

The working system is the oracle. Astrology moves only when the new build reproduces today's package byte for byte and the library sends the same values, screen by screen.

  1. A converter turns each YAML screen into screen.svg, mechanically: every shape has one SVG element (section 3), for becomes data-each, parts are written in place, data tables stay in display.yaml, tap_zone becomes a tap target on the element it covers or an invisible one. The converter names each hole after today's wire field, so the built items read the same fields.
  2. The sky script stays. sky.mjs moves to lib/; each screen's feed calls it and returns SVG-unit values; the wire map brings them back to today's numbers, rounded as today.
  3. The golden test, which must fail before it passes: build both, compare the package bytes; replay every astro.mjs --dry-run command for a fixed set of dates and compare the values sent; render every screen with the reference player and compare pictures pixel for pixel.
  4. Then the YAML screens and the per-skill command-line plumbing go, the docs page for authors becomes one page about SVG, and the YAML converter is kept for one release.

Two places need care: the sign tap area (today a disc of 0.07 plus a 30 degree wedge; in SVG an arc band with data-tap-r="7"), and the lit-ring tokens (lit_ring becomes the literal 7.5). Both are covered by the golden test.
