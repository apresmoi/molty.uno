Molty Display v2

A proposal for how skills describe what Molty draws: a readable display.yaml next to the skill's SKILL.md, plain image files in assets/, and a compiler that turns them into the small package the device already plays.

Status: proposal only. No code, schema or firmware has changed. Today's format (molty-pkg/1) is in docs/PACKAGES.md; nothing here replaces it on the device.

The short version

A skill that draws on Molty is three things side by side:

  • SKILL.md: words for the agent. What the skill does, which screens exist, when to show which.
  • display.yaml: the drawing. Screens made of named shapes, with typed inputs.
  • assets/: plain files (SVG, PNG). The compiler turns them into the device's masks and images.

The five decisions that shape everything else:

  1. The skill folder is the source; the package is a build output. SKILL.md links to screens in display.yaml; the compiler writes the installable package and a generated display.md (every screen's inputs and a ready scene.play call), so the agent docs never drift from the drawing.
  2. One key names the shape, and units never change. - circle: { radius: 0.9 }. Distances are fractions of the screen's radius, angles are degrees counter-clockwise from 3 o'clock, times are seconds. A place is center, {x, y} or {angle, distance}.
  3. Inputs are declared with a type and a sentence; binding is one form only. "{{ value }}" and, inside a for, "{{ body.angle }}". A whole value, never a formula. Any maths stays in the skill.
  4. The device does not change to ship v2. The compiler emits today's molty-pkg/1 exactly. Layouts are only 11 KB of the astrology package's 74 KB (assets are the rest), so a new wire format would buy little. A few small firmware additions (defaults, motion) come later, one at a time.
  5. Two checks before anything ships. A published JSON Schema (editors and agents autocomplete it) and a device check in the compiler (limits after repetition, asset cost against 256 KB, every name resolves). The compiler also writes an input schema per screen, so an agent can check its params before sending.

Design principles

  • Say what it is. circle, arc, tap_zone, radius, reads. No one-letter keys, no k, no a0.
  • Units are part of the language, not of each field. Learn them once (places, units, colors), then every number reads the same.
  • Readable by people and agents alike. YAML to write, JSON accepted, same schema. Every input carries an about sentence.
  • No code. No expressions, no conditions, no filters. Repetition and binding only. Same promise as today.
  • Molty's look by default. Named colors and line weights (ink, grid, hairline) so a new skill looks like Molty without picking hex codes.
  • Small device, smart compiler. Names, units, files and reuse are resolved on the computer; the device gets the same compact JSON as today.
  • v1 keeps working. Every v1 package converts to v2 and back, item for item.
  • snake_case everywhere. One naming style, valid inside {{ }} and in agent JSON.

The skill folder

A small skill keeps every screen in display.yaml. A big one moves each screen into screens/<name>.yaml and lists them by name; shared tokens, assets, data and parts stay in display.yaml.

The compiled package still lands where the device fetches it today: packages/<id>/<id>.json plus its packages/index.json entry. The download allowlist and install flow do not change.

The split form in display.yaml:

screens:
  chart: screens/chart.yaml          # a path: the file holds one screen (about, duration, inputs, draw)
  sign_closeup: screens/sign-closeup.yaml
  dial:                              # or the screen itself, inline. Both can mix.
    about: ...
    draw: [...]

Recommendation: one display.yaml by default; split at about 5 screens or 200 lines. One file is one thing for an agent to read and one place to look. Past that size a file gets hard to scan and two people editing two screens collide. The compiler output is identical either way, so splitting later is a pure move.

molty.json (today: requires, packages, fallback) folds into display.yaml's package block, so the pair stays a pair.

Motion, proposed

move:
  along: "{{ path }}"     # an input of type path: [{ time, x, y }, ...], up to 32
  ease: linear            # linear | smooth

Between two keyframes the shape slides; before the first and after the last it waits there. One dot instead of 14 copies, smooth instead of stepped, and the agent sends 3 to 6 keyframes instead of 14. This one needs the firmware to interpolate (about 40 lines in scene_player.c); until then the compiler refuses move and authors use the stepped v1 form.

Binding: one form

  • "{{ value }}" reads an input. Inside for: body in bodies, "{{ body.angle }}" reads a field of the element.
  • The braces fill a whole value, never part of a string. "Sun in {{ sign }}" is refused: the skill sends the finished sentence.
  • No maths, no filters, no conditions. If it needs a formula, the skill computes it and sends the result.
  • Inside a part, {{ }} reads the part's with values, which may themselves pass an input through.
  • Why {{ }}: agents and editors already know it from every template language; it never collides with a literal; and it reads the same in YAML and JSON. In YAML, quote it ("{{ x }}"), which the schema's error message says.

Paint order inside a for: the compiler draws layer by layer (the first inner shape for every element, then the second for every element). That is what v1's each does, and what a chart wants (all lines under all symbols).

Taps and highlights

- tap_zone:
    at: { angle: "{{ body.angle }}", distance: "{{ body.distance }}" }
    radius: 0.08
    reads: "{{ body.reading }}"   # shown at once, word by word, no round trip
    id: "{{ body.id }}"           # the agent's tap event names it
    highlights: "{{ body.id }}"   # groups to light; left out: whatever is drawn inside the zone
    grow: 1.25                    # how much what it lights grows, 1 to 3
  • along: { from, to } makes the zone a band of radius around a segment: a line you tap along (an aspect).
  • Highlighted shapes grow about their own centre and brighten while the reading plays, then ease back. Shapes with only_when: highlighted appear only then.
  • Overlapping zones: the smallest wins, then the nearest. Same as today.

Assets

Assets are ordinary files in assets/. An asset's name is its file name without the extension (assets/signs/aries.svg is aries); folders are for tidiness, and two files with the same name are an error.

assets:
  - files: assets/signs/*.svg     # aries ... pisces
    as: symbol                    # one color, takes the shape's color
    pixels: 64                    # width on the device; height keeps the aspect
    stroke: 0.085                 # SVG lines drawn this thick (fraction of the drawing)
  - files: assets/planets/*.svg
    as: symbol
    pixels: 32
  - files: assets/maps/*-map.png  # sun-map, moon-map ...: wrapped round globes
    as: map
    pixels: [128, 64]             # equirectangular, 2:1
  - file: assets/logo.png
    as: picture                   # keeps its colors: up to 15 + transparent
    pixels: 48
asfrombecomes (v1)cost on the device
symbolSVG (strokes and fills) or PNG (alpha)mask, 1 bit a pixel64 x 64: about 0.7 KB
picturePNG, SVGimage, 4 bits a pixel, 15 colors chosen by the compiler48 x 48: about 1.6 KB
mapPNG, 2:1image (a globe's map)128 x 64: about 5.5 KB

Generated art (the noise-made planet maps, the ring masks at five tilts) becomes a small script that writes PNGs into assets/ once; the PNGs are what is checked in and reviewed. The compiler only reads files.

SKILL.md and display.yaml together

  • SKILL.md says when and why; display.yaml says how it looks. Neither repeats the other.
  • SKILL.md names a screen with a plain markdown link: [chart](display.yaml#chart). Any markdown viewer follows it; the checker makes sure every such link names a real screen, and warns about screens SKILL.md never mentions.
  • For the exact inputs, SKILL.md links the generated build/display.md: per screen, its about, duration, an input table built from each about, and a ready scene.play call filled with the example values. Today's hand-written references/layouts.md goes away.
  • SKILL.md's frontmatter stays the standard name + description, so every agent harness still loads it.
  • The commands are unchanged: scene.play { pkg, layout, params, ttl_s }, where layout is the screen's name.

Example 1: a tappable dial

A gauge with twelve marks, a pointer at an angle the agent sends, and a centre you tap to read a sentence.

v1 today 
"dial": {
  "dur": 0,
  "params": { "value": "number",
              "reading": "text" },
  "items": [
    { "k": "ring", "r": 0.9, "w": 0.012,
      "color": "#c8cce0" },
    { "k": "ticks", "r": 0.82, "len": 0.08,
      "n": 12, "a0": 0, "w": 0.012,
      "color": "#565b72" },
    { "k": "ticks", "r": 0, "len": 0.8,
      "n": 1, "a0": "$value", "w": 0.06,
      "color": "#ffffff" },
    { "k": "disc", "r": 0.05,
      "color": "#ffffff" },
    { "k": "spot", "r": 0.3,
      "say": "$reading", "id": "centre" }
  ]
}
v2 display.yaml 
# yaml-language-server:
#   $schema=../../schema/display-2.json
molty: display/2
package:
  id: dial
  name: Dial
  version: 1.0.0
  about: A gauge with a pointer and a tap-to-read centre.

screens:
  dial:
    about: A gauge pointing at one value.
    duration: hold
    inputs:
      value:
        type: angle
        about: Where the pointer points.
        example: 135
      reading:
        type: reading
        about: What a tap on the centre shows.
        example: Humidity 64 percent, a bit damp.
    draw:
      - circle: { radius: 0.9, width: hairline,
                  color: ink }
      - ticks: { count: 12, radius: 0.82, length: 0.08,
                 width: hairline, color: grid }
      - spoke: { angle: "{{ value }}", length: 0.8,
                 width: bold }
      - dot: { radius: 0.05 }
      - tap_zone: { radius: 0.3, id: centre,
                    reads: "{{ reading }}" }

skills/molty-dial/SKILL.md

---
name: molty-dial
description: >-
  Show one value as a gauge on your human's Molty, with a sentence they can
  tap to read. Use when a single number has a natural range (humidity,
  battery, progress) and the molty skill is paired.
---

# Molty dial

Molty draws a [dial](display.yaml#dial): a ring of twelve marks and a pointer.
The skill turns the value into an angle and writes one sentence about it.

## Show it

1. Map the value onto 0..300 degrees: `angle = 240 - 300 * (value - min) / (max - min)`.
2. Send `scene.play` with `layout: "dial"` and `{ value: angle, reading }`.
   Inputs and a sample call: [build/display.md](build/display.md#dial).
3. Speak one short line; the reading is on the screen for a tap.

The package installs on first use (Molty asks your human with one tap).

# Molty astro

This skill computes the sky (scripts/sky.mjs); Molty only draws it.
Every screen, its inputs and a sample call: [build/display.md](build/display.md).

## Which screen when

- "What's in the sky tonight?": [globe](display.yaml#globe) for the Moon, then each
  planet, [saturn](display.yaml#saturn), then [sign](display.yaml#sign) for the Moon's sign.
- "Show me my chart" or a horoscope question: [chart](display.yaml#chart), held.
  A tap on a sign: play [sign_closeup](display.yaml#sign_closeup) and queue the chart behind it.
- "What does trine mean?": [aspect](display.yaml#aspect), five seconds each.
- "When is the next eclipse?": [solar_eclipse](display.yaml#solar_eclipse) or
  [lunar_eclipse](display.yaml#lunar_eclipse).

## Run it

node "<skill-dir>/scripts/astro.mjs" chart --interactive
...the rest as today: install once, speak first, short lines...

move and default both need small firmware additions (next section). Until they land, this screen is written in the stepped form: for: key in path with a dot that has show: { from: "{{ key.from }}", until: "{{ key.until }}" }, which compiles to exactly today's item.

The schema checks shape and spelling. What it cannot know (does this binding name a declared input, does the screen fit in 128 items with 32 bodies, does the asset exist) the compiler checks next.

Check, build, preview, publish

1. WriteSKILL.md, display.yaml (or JSON), files in assets/. The editor autocompletes from the schema.
→
2. Checkmolty-display check: schema, then device rules, then SKILL.md links.
→
3. Buildmolty-display build: assets to masks and images, screens to v1 layouts, cost report, display.md, input schemas.
→
4. Previewmolty-display preview: a local browser page. Pick a screen, edit inputs, scrub time, tap zones.
→
5. PublishCommit the skill and the built package. check-packages proves the build reproduces; Molty installs it as today.

What each check catches

layercatches
JSON SchemaUnknown keys, misspelt shapes, wrong types, a color that is neither a token nor #rrggbb, a missing about.
Device rules (compiler)Bindings name declared inputs of a matching type; {{ body.x }} only inside for: body in ...; assets and tokens exist; at most 64 items a screen, 8 inputs, 32 screens, 64 assets of 128 px; the worst case (every list at its max) stays within 128 items, 40 letters and 32 groups; literal text never starts with $ or @ (v1 reserves them); the package fits 256 KB.
Skill linksEvery display.yaml#name in SKILL.md is a real screen; screens SKILL.md never mentions are listed.
Agent side, at run timebuild/inputs/<screen>.schema.json lets the skill (or the relay, later) check params before scene.play, instead of the device answering bad_params.

Errors name the file, the line and the fix: screens/chart.yaml:41 symbol.asset "{{ body.glyph }}": bodies has no field glyph (fields: symbol, angle, distance, color, reading, id).

The preview reuses packages/tools/play.mjs (the braille lattice and --hd views) on the compiled layout, so what you see is what the device would draw.

What the device keeps

Phase 1 ships with no firmware change: the compiler's output is a molty-pkg/1 file that pkg_parse.c already accepts. Each feature below that needs the device is optional and small; the compiler refuses it until the firmware advertises it.

featurephase 1 (no firmware change)firmware addition
Input defaultDocumented in display.md; the agent must still send every input.Optional params with a default in the layout; a few lines in the param check.
move along a pathRefused; use the stepped show form.Interpolate x, y between keyframes in scene_player.c.
lit_side: right | left from an inputA literal word is fine; an input sends 1 or -1.Accept the words at run time.
Polar from/to on a line from inputsLiteral polar is converted at build time; bound points must be {x, y}.A polar flag per point.
Text with a slot ("Sun in {{ sign }}")Refused; send the finished text.Not planned: keeps the device free of string building.

Why not a new compact wire format? The astrology package is 74 KB: 63 KB of assets (base64 masks and images) and 11 KB of layouts. Shrinking layouts would save little; a binary asset encoding would save the base64 third, but is a separate decision (open question 4).

Moving from v1

  • molty-display convert packages/astrology/astrology.json --to skills/molty-astro writes a display.yaml and turns every asset back into a PNG in assets/.
  • The conversion is mechanical: k to the shape name, $x to {{ x }}, each run of "each": "$bodies" to a for block, polar to {angle, distance}, hex colors that match a token to the token.
  • It cannot guess what @a means, so list fields keep their v1 names and every input gets about: TODO, which the checker reports until a person or agent fills it in. Renaming a to angle is then a find-and-replace the checker verifies.
  • The guarantee: for every package in the repo, build(convert(v1)) produces the same layouts and assets as the v1 file. A test runs it on all of them and fails on any difference.
  • The device keeps reading v1 files forever; nothing installed today needs reinstalling.
  • Creature packages (duck, cat, octopus) stay as they are: their rig and clips come from Blender and tools/creatures/kit.mjs. See open question 5.

Open questions for Juan

  1. Angles: maths or clock? This proposal keeps today's maths convention (0 at 3 o'clock, counter-clockwise). A clock convention (0 at 12, clockwise) reads more naturally to people but breaks every v1 number and the astrology formulas. Keep maths?
  2. Asset names: file name or path? Bare file names (aries) need no firmware change but force unique names (sun vs sun-map). Paths (signs/aries) read better and need the firmware to allow / in names, one character in key_ok.
  3. Rename layout to screen in the command? The docs would say screen everywhere; the wire can keep layout with the relay accepting both.
  4. Binary assets? Shipping masks and images as raw bytes instead of base64 cuts about a third of a package. Worth a format change now, or later when a package nears 256 KB?
  5. Creatures in the same pair? Should a creature also be a skill folder with a creature.yaml, or stay a Blender-built package outside this format?
  6. Where does the schema live? schema/display-2.json in this repo (raw GitHub URL), or a stable molty.uno/schema/... address that survives a repo move?
  7. One file or split by default? The recommendation is one file until about 5 screens. Would you rather every skill start split, so they all look alike?
