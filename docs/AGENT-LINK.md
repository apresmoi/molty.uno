# Agent link — v0 spec

**Status:** v0. Goal: any agent, anywhere, drives Molty with **no laptop in the loop**.
Built to be swapped module by module. Background and design rationale:
[ARCHITECTURE.md](ARCHITECTURE.md).

```
Molty (home Wi-Fi) ──outbound WSS──▶ molty-relay (Cloudflare Worker + Durable Object)
                                       ├─ /mcp   remote MCP (HTTPS)   ◀── any MCP client (Claude, Grok, …)
                                       ├─ /v1/*  REST                 ◀── molty CLI --relay, scripts
                                       ├─ voice  TTS/STT provider     (Workers AI first; swappable)
                                       ├─ /v1/voice  voice box (WSS)  ◀── the owner's own STT/TTS box (molty-voice)
                                       └─ (later) OpenClaw node adapter
```

## Modules and seams (each swappable)

| Module | Where | Swappable seam |
|---|---|---|
| Relay core (rooms, auth, pairing, routing, jobs) | `services/relay/src/core/` | pure TS, no Cloudflare imports |
| Relay host | `services/relay/src/worker.ts` (+ DO) | another host (Node server) wraps the same core |
| Agent surfaces | `src/surfaces/mcp.ts`, `src/surfaces/rest.ts` | add OpenClaw node adapter beside them |
| Voice provider | `src/voice/*.ts` → `interface VoiceProvider { tts(text, opts) → PCM16@16k; stt(PCM16@16k) → text; ttsStream?; sttStream? }` | workers-ai · openai · none (env) · box (the owner's [voice box](#voice-box), per device) |
| Device link client | `device/firmware/main/link/` | transport only; commands come from the dispatcher |
| Device command dispatcher | `main/link/link_cmd.c` | ONE registry used by both the WSS link and (later) local HTTP |
| Pairing UI | static: the 4-digit code alone, held as one centred token in the fluid text target (no ORP accent), until accept/reject/timeout (`link_ui_show_pair`); agent name is shown by the console via `GET /api/link` | a dedicated `pair` creature state is the planned upgrade |

## Identities and secrets

- `device_id` = `molty-` + 10 random chars `[a-z2-9]` (e.g. `molty-k7m2w9c4ya`). Public,
  generated together with the key on first boot and persisted in NVS. It is unrelated to
  the MAC; unpredictable IDs prevent guessing a new device's TOFU room before it connects.
- `device_key` = 32 random bytes, generated with the ID on first boot, kept in NVS. The device sends
  it on every connect. The relay stores `sha256(device_key)` on first claim of a
  `device_id` (trust on first use); later connects must match. Console "forget link" sends
  `{"t":"forget"}` on the authenticated socket, waits up to 3 s for close 4410, then wipes
  the NVS identity and relay URL. The next identity has a fresh ID **and** key. If offline
  or the relay does not acknowledge, local erasure still proceeds; remote revocation is
  confirmed only by 4410. Older key-only installations migrate to a new random ID/key.
- `link_code` = 8 chars `[A-Z2-9]`, generated by the device, shown in the console's
  "Connect an agent" instructions, rotates every 15 min and after each successful pairing.
  Stops strangers from spamming pair requests: a pair request must carry a valid link_code.
- `agent_token` = 32 random bytes (base64url), issued by the relay after on-device approval.
  Relay stores only its hash, scoped to one `device_id`, with the agent's name. Revocable.

## Pairing flow

1. Console (USB or `molty.local`) → Wi-Fi set → "Connect an agent" → the user pastes ONE
   message into any agent:
   ```
   Hi! Please connect yourself to my Molty.

   Skill: https://github.com/apresmoi/molty.uno/tree/main/skills/molty
   Device: molty-xxxxxxxxxx
   Code: K7M2W9C4
   Relay: https://<relay>        (only when the device uses a relay other than the default)

   I'll tap Molty to accept you.
   ```
   The agent-facing guide is the [agent skill](#agent-skill-and-api_version) (`skills/molty/`):
   what Molty is, pairing over plain HTTPS, the REST and MCP surfaces, events, latency and
   etiquette. Claude Code and Codex install it as the `molty` plugin; the console shows both
   install lines above the message.
2. The agent calls `POST /v1/pair {device_id, link_code, agent_name}` (or the `molty_pair` MCP
   tool, which is the only tool usable without a token). The request long-polls ≤ 120 s.
3. Relay → device: `pair.request {req, agent_name, code}` where `code` is 4 digits.
4. Device shows the 4-digit `code` statically (one held token in the fluid) until decided
   (touch tap or BOOT button = accept; PWR = reject; 110 s = `timeout`, so the device
   decides just before the relay's 120 s window closes). The console polls `GET /api/link`
   (~1 Hz) and advances on `pair` / `last_pair`.
5. Device → relay: `pair.result {req, ok}`; failures include `reason:"timeout"` or
   `reason:"rejected"`. On ok the relay mints `agent_token` and returns it to the waiting
   request: `{agent_token, device_id, api_version}`. Device rotates `link_code` and reports the new code
   on the same connection. Successful `pair.result` also carries the new `link_code`,
   allowing the relay to replace the old code within its approval transaction.

## Device ↔ relay wire (WS/WSS `/v1/device?id=<device_id>`)

First frame from device: `{"t":"hello","id":"molty-k7m2w9c4ya","key":"<b64 device_key>","fw":"...","caps":["fluid","say","say_cues","say_marks","listen","listen_stop","listen_window","ack","shake_talk","show","mood","act","creature","react","ask","log_upload"],"board":"waveshare-esp32-s3-touch-lcd-1.46","link_code":"..."}`
→ relay answers `{"t":"welcome","features":["listen_adopt"],"now":<relay unix ms>,"log":{"max_lines":48}}` or closes with 4401.
`features` lists what the relay does for the device (`listen_adopt`: it adopts a listen the device
began by itself — [Shake to talk](#shake-to-talk)); `now` is the device's time sync and `log` says the
relay takes device log uploads ([Activity log](#activity-log)). Older relays send none of them, and
the device then never starts a shake listen nor uploads.

`board` names the hardware (`device/firmware/boards/`, see [PORTING.md](PORTING.md)). `caps`
lists `say` / `listen` only when the board has a speaker / microphone (`say_cues` with `say`,
firmware that shows a say's words as they are spoken; `say_marks` with `say`, firmware that
fires a say's inline cues on their word — see [Inline cues and actions](#inline-cues-and-actions); `listen_stop` with
`listen`, firmware that can end a listen on the relay's word; `listen_window` with `listen`,
firmware whose window is optional, 0..30000 or unlimited — see `listen` below; `ack` with
`listen`, firmware that acknowledges the end of a turn itself — see [Turn acknowledgement](#turn-acknowledgement); `shake_talk` on
boards with a mic and an IMU, firmware whose shake can start a listen — see [Shake to talk](#shake-to-talk)), `ask` only when it
has a touch screen (and firmware that implements `ask`), and `update` when the firmware can
install a release itself ([Firmware updates](#firmware-updates)), `act` when it plays one-shot
gestures ([Inline cues and actions](#inline-cues-and-actions)), `log_upload` when it
sends its log lines to the relay ([Activity log](#activity-log)), `trace` when its listen frames
carry the [turn trace](#turn-trace) fields, and `hints` when it takes `hint` frames (listener
reactions, [Turn trace](#turn-trace)); the relay answers
those commands `409 unsupported` up front, without calling TTS, when the device left them
out — or `409 firmware_too_old` when `fw` is older than the feature's minimum firmware
(`FEATURES` in `services/relay/src/core/version.ts`): caps say whether it can, the version says why not. The device itself answers a command its board cannot do with `error:"unsupported"`
(an unknown command is `unknown_command`).

Configure a relay origin (`wss://host` or `ws://LAN-IP:8787` for `wrangler dev`);
the device appends `/v1/device?id=<device_id>`. WSS verifies certificates/hostnames.
Close codes: **4400** malformed, **4401** bad key, **4409** replaced by a newer socket,
**4410** forgotten. A 4401 retries every 5 minutes and sets `auth_failed:true` in local
`GET /api/link` until welcome or local reconfiguration. Other disconnects use 1–60 s
backoff. Local status also includes `close_code` for the current/last attempt.

Text frames are JSON:
- relay→device `{"t":"cmd","id":"c17","name":"show","args":{...}}`
- device→relay `{"t":"res","id":"c17","ok":true,"result":{...}}` or `{"ok":false,"error":"code"}`
- device→relay `{"t":"evt","name":"shake|tap|button|answer|say.done|link_code|...","data":{...}}`;
  `shake`/`tap`/`button`/`answer` reach agents (see [Device events](#device-events) and [Events](#events-device--agents)), the rest is relay-internal.
- `pair.request` / `pair.result` as above; `{"t":"ping"}`/`{"t":"pong"}` every 20 s.
- device→relay on each rotation: `{"t":"link_code","code":"...","link_code":"..."}`.
  `code` is the requested spelling; `link_code` is a compatibility alias required by
  the built relay's current `room.ts` handler. Rotation does not reconnect the socket.
- device→relay `{"t":"forget"}`; relay revokes its room's bindings/tokens/jobs, sends
  `{"t":"forgotten"}`, then closes 4410. Local POST `/api/link/forget` returns 202 pending
  while the device performs this bounded exchange before erasing its identity.

Binary frames carry audio: `<JSON header>\n<payload>` (header ≤ 512 B, payload ≤ 16 KB).
Header: `{"s":"<stream id>","seq":N,"kind":"pcm16","rate":16000,"end":bool}`.
- Stream IDs allow 1–128 characters; omitted `end` means false. Header-only binary
  frames (without a newline/payload) are accepted. PCM payloads contain whole int16 samples.
  Text-frame limit is 64 KiB, independently of the audio-frame limit.
- **Listen frames are ordered by `seq`** (0, 1, 2, … per listen). Firmware with the cap `trace`
  keeps a frame whose send failed (a ring of ≤ 10 s on the device) and resends it in order, same
  seq; it skips a seq only when that ring overflowed (the audio is gone). The relay takes frames
  in seq order: a frame ahead of a gap waits (≤ 64 frames); a duplicate is dropped; a gap still
  open 1 s after the first frame waiting behind it (the end frame included) is given up — counted
  lost in the [turn trace](#turn-trace) — and what waited flows on. Streaming STT always gets the
  audio in seq order. Frames after the end (or after the box's turn end) are dropped as before
  (counted `late`). Older firmware sends in order and never resends: nothing changes for it.
- **Turn trace fields** (listen frames, firmware cap `trace`; all optional, a malformed one is
  dropped, never fatal; older relays ignore them): `ct` capture ms of the frame's first sample
  from the listen's mic start (a shake listen: from the shake's mic start; after a settle trim
  the first frame's `ct` is the trim); `lv` hex, one byte per 100 ms chunk of the frame = the
  chunk's RMS level `clamp(round(2·(dBFS+100)), 0, 200)` (0 = ≤ −100 dBFS or silence, 200 = 0
  dBFS); `cl` samples saturated after the mic gain (omitted when 0); `rt` failed send attempts
  of this frame before it went out (omitted when 0); `wq` ms it waited on the device between its
  capture end and its send. The end frame adds `tr` (the whole header stays ≤ 512 B):
  `{wall, cap, sent, fail, drop, dropms, r0, r1, gain, pk, set, setc}` — ms from mic open to
  the end, ms of audio captured (after the trim), frames sent, failed send attempts, frames
  dropped by the device ring and their ms, RSSI (dBm) at the listen's start and end, the mic
  gain, the peak |sample| in ‰ of full scale, and for a shake listen the ms of handling noise
  trimmed and `setc:1` when that settle hit its cap ([Shake to talk](#shake-to-talk)).
- **`hint`** (relay → device, firmware cap `hints`): `{"t":"hint","job":"<listen job>","k":"pause"|"question"}`,
  fire-and-forget (no `res`), forwarded from the voice box's `stt.hint` while that listen is open.
  The device ignores a hint for anything but its running listen; older firmware ignores the
  unknown `t`. What the device does with it: [Turn trace](#turn-trace) › listener reactions.
- `say`: relay sends `cmd say {job,text,ms,rate:16000,voice?,cues?}`; device starts `speaking`
  and text immediately, then acknowledges. Relay sends 320 ms PCM frames (`s` = job id),
  with three lead frames and paced delivery thereafter. TTS is streamed: the relay sends
  `cmd say` once the first sentence is synthesised — with the voice box, at once, in parallel
  with the synthesis (its first audio is ~0.25 s away) — and streams while the rest is still
  being synthesised, so `ms` is then an estimate (informational; exact when synthesis finished
  first). The first frame leaves once it holds 160 ms (or after 100 ms), not a full chunk. A
  frame may be shorter than 320 ms when the device would otherwise run dry, and the last one
  may be header-only (`end:true`, no payload) when synthesis ended after the last audio frame
  left (or, with the box, when synthesis failed before any audio). After the last frame leaves
  the ring **and I2S DMA**, device returns to idle (unless an explicit mood arrived during the
  say) and sends
  `{"t":"evt","name":"say.done","data":{"job":"..."}}`. Failed/cancelled playback
  does not emit successful completion.
  **Word-timed text (cap `say_cues`)**: the relay adds `cues:true` and the frames' headers carry
  word cues `"w":[[word, sample], ...]` (≤ 20 per header; word = 0-based index of the text's
  whitespace-split words, as the speed reader counts them, < 512; sample = 16 kHz offset from
  the stream's first sample). A cue goes out with or before the frame holding its audio; cues
  that do not fit before the end go in header-only frames just before it. The device shows no
  word until word 0 is cued, and word k once the speaker's position (samples written to I2S
  minus the DMA ring) is within 30 ms of its cue — the lead covers the estimate's bias, the
  reader's frame and the 15 ms write cadence, so the word reaches the glass with its voice;
  when playback is over, the remaining cued words, then the reader's own pace. Cues come from
  the voice box's own word timing (Kyutai's TTS `Text {start_s}` less its one-step lag, `tts.word` below, offset by
  the audio of the segments before it); any word without one — every word with the cloud — is
  estimated when its segment's audio is complete, from its real length in proportion to
  characters. A malformed cue list is a malformed frame (the stream ends). Firmware without
  the cap gets neither: its reader runs at its own pace as before.
  **Marks (cap `say_marks`, with `say_cues`)**: `cmd say` adds `marks: [[word, "name"], ...]`
  (≤ 16, in text order; `word` 0..4096; `name` a mood or an action) — the agent's inline cues,
  already stripped from `text`. The device fires mark k when word `word` is revealed (its word
  cue, the same instant), or when playback ends cleanly for a word with no cue (past the last
  word, or past word 511); a cancelled or failed say fires none of the rest. Malformed marks
  refuse the say (`invalid_args`); marks without `cues:true` are ignored. What firing does:
  [Inline cues and actions](#inline-cues-and-actions).
  `talk` requires this `say.done` before it opens the mic: none within the streamed playback
  time + 2.5 s fails the turn with `playback_timeout` (REST 504); an elapsed estimate is never
  taken as playback.
- TTS cancellation: a segment that misses its timeout (`tts_timeout`), or a stream nobody reads
  any more (device done/gone, turn failed), aborts the provider's request/stream (`TtsOptions.signal`):
  Workers AI cancels the model stream even mid-read, OpenAI aborts the fetch.
  **Limit (Workers AI):** `env.AI.run()` takes no signal, so a call still waiting for the
  binding's answer cannot be cancelled: the turn fails on time (`tts_timeout`), but that
  `run()` stays pending until Workers AI answers, and its output is then released unread.
  Likewise a non-streamed (whole-body) TTS reply is read to the end once it has started.
  Whether Workers AI keeps computing (and billing) an abandoned request is not verified.
- `ask`: relay sends `cmd ask {job, options, colors, timeout_ms}` (`options` 1–5 strings, each 1–8
  chars of printable ASCII 0x20–0x7E, not all spaces, unique ignoring case; `colors` one
  `"#rrggbb"` per option, in order — the relay always sends them, resolved from the agent's
  names / hex or the defaults by index; `timeout_ms` integer 1000..120000); the device
  validates the same (`invalid_args`; `colors` is optional to the device: absent → its own
  defaults by index, present → exactly one valid hex per option), answers `unsupported`
  without touch, and acknowledges `{job}` at once. Firmware from before colours ignores the
  extra field (unknown args are not checked), so the relay needs no cap for it. The options
  condense out of the fluid in sectors (`device/firmware/main/fluid/fluid_ask.h`: 1 = whole screen,
  2 = left / right, 3–5 = pie sectors from 12 o'clock clockwise, options in reading order of
  the sectors), each label in its colour (pastel palette; mono palettes stay one hue), with a
  rim arc of the fluid in that colour spanning its sector minus a small gap at each faint
  divider (1 option: a full ring). On a tap the chosen arc flares and settles while the
  others fade with their labels. The device then sends exactly one `answer` event for the job:
  `{"t":"evt","name":"answer","data":{"job":"…","index":1,"label":"no"}}` (a tap: the sector
  it landed in; `label` = `options[index]` verbatim, no `reason`),
  `{"t":"evt","name":"answer","data":{"job":"…","index":null,"reason":"timeout"}}` (no tap
  within `timeout_ms`), or `{…,"index":null,"reason":"cancelled"}` (an accepted `say`,
  `show`, `mood`, `state` with args, `listen` or a new `ask`, or a pairing, took the screen
  first — a command the device refuses leaves the question up; a new `ask` cancels the old
  one before its own ack). Events go out only while the link is up: a question pending when
  the link drops ends on screen with no event. While a question is pending, no tap is a `tap`
  event, and a tap answers it only when the panel shows it: a tap on a frame still showing a
  question it replaced, or the letters morphing into its labels (until they condensed), answers
  nothing. A tap's capture time decides against `timeout_ms`: at or before it, the tap wins
  over the timeout; after it, the timeout wins.
  Relay side (`molty_ask` / `POST …/ask`): the `cmd ask` goes out only after the optional
  `say` has played (its `say.done`, as `talk`), with labels already trimmed (`MAX_ASK_LABEL`
  in `services/relay/src/core/commands.ts`). The relay drops an `answer` unless its job is an ask still
  waiting, `index` is within that job's options, `label` (optional) equals `options[index]`, and
  a tap carries no `reason` / a non-answer no label. No answer within `timeout_ms` + 5 s: the
  relay resolves `timeout` itself; device gone mid-ask: `reason:"offline"`. An answer the relay
  accepted stands even when the `cmd ask` ack is then lost (`device_timeout`): the job is done
  with it (one `answer` inbox event). A lost ack is "delivery unknown", not a failure: the relay
  keeps waiting, and an answer arriving later still ends the job; none by `timeout_ms` + 5 s
  (counted from the ack timeout) resolves `timeout`.
- `listen`: relay sends `cmd listen {job, ms?, rate:16000, end_silence_ms?, no_speech_ms?, vad?, ring_color?, ack?}`
  (`ms` = maximum window, a ceiling — every listen ends early on end of speech / turn.
  **Firmware with the cap `listen_window`**: `ms` 1..30000, or `0` = unlimited (it ends only on
  end of speech / turn, no_speech, the relay's `listen_stop`, or a 300 s safety ceiling →
  `reason:"max"`); sent only when the agent gave one — absent, the device applies its own
  setting (console, 5..30 s or unlimited, NVS, 30000 out of the box; `POST /api/creature/state
  {listen_ms}`), like `ring_color`. Its answer carries the window it applies: `{job, ms}`
  (`0` = unlimited; cap `ack` firmware adds `ack`, see [Turn acknowledgement](#turn-acknowledgement);
  newer firmware adds `filler_ms`, the owner's [auto filler](#quick-phrases-and-the-auto-filler) delay), and the relay waits that long (the ceiling for 0) + 5 s for the end frame.
  The mic streams in 100 ms chunks: no device buffer is sized by the window. **Older firmware**
  (no cap) takes 1..10000 and always gets `ms` (10000 when the agent gave none); an agent's
  `0` or > 10000 is refused up front, `409 unsupported`. The VAD knobs only when the agent gave them: `end_silence_ms`
  300..3000, `no_speech_ms` 1000..10000, `vad` bool; `ring_color` `"#rrggbb"`, resolved by the
  relay, only when the agent gave one — else the device's default, see the console's
  `ring_color`; older firmware ignores it). Device streams mic PCM up; the last frame
  (`end:true`) may carry `"reason":"silence"|"no_speech"|"max"|"error"` and `"speech_ms":N`
  (device end-of-speech). `speech_ms` is present only when the device measured it: absent with
  `vad:false` and when the listen ended inside VAD calibration (unknown, not 0). Relay runs STT
  the moment `end` arrives, except when `reason` is `no_speech`: then no STT call, transcript
  `""`. `speech_ms` alone never skips STT (firmware before this change sent `speech_ms:0` with
  `vad:false`). Older firmware sends no reason: STT as before, reason derived (`max` window
  full, `ended` stopped early, `no_speech` empty transcript).
- `say_cancel` (cap `say_cancel`): relay sends `cmd say_cancel {job}` when a say / talk / quick job fails: the device stops waiting for that say's audio (`{job, cancelling}`; any other job is a no-op). Without audio a say also gives up by itself after 8 s (30 s once frames have arrived).
- `gestures` (cap `gestures`): `cmd gestures {bindings?}` sets `{tap|double_tap|button_accept|button_reject: none|talk|event|stop}` (NVS) and answers `{bindings}`; a tap during a recording ends it with reason `tap`, whatever is bound.
- `listen_stop` (cap `listen_stop`, boards with a mic): relay sends `cmd listen_stop {job, reason}`
  when its STT called the end of the listen (a [voice box](#voice-box) `stt.turn_end`): `reason`
  `"turn_end"` (the human finished) or `"no_speech"` (the box heard nobody). The device ends THAT
  listen within one 100 ms chunk, as if its VAD had fired: the frames recorded so far go up, the
  last with `end:true` and that `reason`, and its [turn acknowledgement](#turn-acknowledgement)
  rules apply to it — `no_speech` gets no chirp and no thinking. `reason` absent = `turn_end`
  (older relays); any other value is refused. Firmware older than the reason ignores it and ends
  with `turn_end` (so it chirps on a box no_speech). Answer `{job, stopping:bool}`
  (`false`: not the running listen — already ended, another job, or a say; nothing changes).
  It never cancels and never touches a say. The relay does not wait for that end frame: the job
  is already done (`reason:"turn_end"`, `timings.turn_end` = ms from the listen's start to the
  turn end) and frames arriving after the turn end are dropped. **Firmware without the cap** is
  not sent the command: the job still finishes at the turn end, but the mic stays open until the
  device's own end (silence / no_speech / its window), and those frames are dropped; a say or
  listen sent in that gap is answered busy by the device.
  `listen_stop` naming a [shake's listen](#shake-to-talk) still waiting to be adopted (its local
  id) declines it, whatever the reason: it ends quietly.
- `listen {job, adopt: <local id>, rate, ms?, vad?, end_silence_ms?, no_speech_ms?, ack?}`
  ([Shake to talk](#shake-to-talk)): the relay takes the listen the device began on a shake as
  its job `job`. Checked like a listen; answered like one (`{job, ms, ack, filler_ms}`); refused
  `listen_gone` when that listen is not waiting any more (never `busy`).


- `update` (relay call `molty_update`): see [Firmware updates](#firmware-updates) for
  `cmd update {job, version, url, sha256, size, timeout_ms}` and the device's `update` events.

Automatic moods around talking: the device sets `listening` on `listen` and `speaking` on
`say` (then `idle`). Firmware with the cap `ack` puts up `thinking` itself the moment a listen
that heard speech ends (with a chirp; [Turn acknowledgement](#turn-acknowledgement)); for it the
relay sends no automatic `thinking`, only `idle` when the transcript comes back empty and the
device had put thinking up (its listen answer said `ack` `chirp` or `thinking`). For older
firmware the relay sends `mood thinking hold_s:15` the moment a listen's end frame
arrives with speech (while STT runs), re-sends it after STT, or `idle` when the transcript is
empty. So the creature thinks from end of speech until the agent's next command (≤ 30 s with
`ack`, ≤ 15 s before).
Agents don't need `mood` calls around talking; an explicit `mood` still wins: once the device
has accepted a `mood` from any agent after a listen began, the relay sends no more automatic
moods for that listen (none while that `mood` awaits its answer either; a refused one does not
count). The same for an `ask` sent after a listen began (any `mood` cancels a pending question
on the device): no automatic mood while its `cmd ask` awaits the ack, none for that listen once
the device showed it (or its ack was lost). On the device, a listen/say that ends falls back to `idle` only if no explicit mood (link
`mood` command, or a local `POST /api/creature/state` with a `mood`) arrived since it started, so
the explicit mood keeps its own `hold_s`; likewise a self-update's progress ("update", "40%", …)
owns the screen once shown (`link_cmd_screen_claim`), so an older listen/say ending mid-download
does not put idle over it.

### Turn acknowledgement

No dead air after the human finishes: the agent's answer takes seconds (STT, the model, TTS),
so firmware with the cap `ack` acknowledges the turn **itself, locally, at once** — no network:

- **When.** A listen ends with `reason` `turn_end` (the relay's end of turn), `silence` (the
  device VAD's end of speech) or `max` with ≥ 160 ms of measured speech — and nothing else took
  the screen during the listen (an explicit `mood`, an `ask`, an update screen, a pairing).
  Never on `no_speech` (the device's own, or a `listen_stop` with `reason:"no_speech"`), `error`
  or a cancelled listen. Decided by the device when the end frame
  leaves (`link_ack_decide`, `device/firmware/main/link/link_protocol.h`).
- **What.** A chirp (`device/firmware/main/audio/chirp.h`: G5 784 Hz → D6 1175 Hz, a rising fifth,
  160 ms, soft raised-cosine attack / exponential decay, peak −17 dBFS, scaled by the speaker
  volume like a say) and the `thinking` mood, the listening ring melting out. `thinking` holds
  30 s at most (then idle) and is the device's own mood: the agent's next `say` (speaking),
  `listen`, `mood` or `ask` replaces it as usual.
- **Audio.** The chirp plays after the listen is reported done, so a `say` / `listen` sent
  meanwhile is accepted at once; it waits until the chirp ends — or cuts it (4 ms fade, the DMA
  ring flushed with silence, ≤ ~110 ms) — and only then starts: the chirp never plays over a
  say and the next listen's mic never records it. A speaker owned by something else: no chirp.
- **Setting.** The human's choice, console Settings › Molty "acknowledge" (`POST
  /api/creature/state {ack: "chirp"|"thinking"|"off"}`, GET reports it, kept in NVS like
  `ring_color`): chirp + thinking (default), thinking only, off.
- **Per listen.** `listen` / `talk` take `ack`: `true` (default) = the setting, `"silent"` =
  thinking without the chirp, `false` = none — an agent can only turn it down. The relay
  validates it and forwards it only to firmware with the cap. The device's listen answer
  reports what it will do (`ack`: `chirp` | `thinking` | `off`).

### Quick phrases and the auto filler

A slow agent (a cold start, a big model) leaves seconds of silence after the human finishes;
the chirp is not words. Two relay features fill it (`services/relay/src/core/phrases.ts`):

```
human stops ─▶ chirp + thinking (device)
   agent: quick {id} ─▶ cached audio at once ─▶ talk queued behind it ─▶ answer, no TTS gap
   no agent action within filler_ms ─▶ relay: a built-in filler ─▶ agent's answer queues behind it
```

- **Quick phrases.** Each agent registers its own short phrases (`phr:<token hash>`; ≤ 20, each
  ≤ 60 characters, ids `[a-z0-9][a-z0-9_-]{0,23}`, inline cues allowed; `filler: true` = Molty may
  use it as its own filler for this agent; `for: question | request | hard | any` = the turns it
  fits; REST `GET|POST|DELETE /v1/devices/<id>/phrases`, MCP `molty_phrases`); built-ins for
  everyone: `hmm`, `one_sec`, `let_me_see` (any), `let_me_think` (hard), `good_question`
  (question), `on_it`, `checking` (request). An agent's id shadows a built-in for that agent;
  nobody else sees or plays its phrases. `builtins: false` (set) turns the built-ins off for that
  agent: not listed, `quick` with a built-in id → `not_found`.
- **Pre-synthesis + cache.** A phrase's audio (PCM + word cues) is synthesised when it is
  registered, in the voice Molty speaks with now (`voice_mode`, the box's default voice), and
  cached per voice + text (`pcm:` meta, `pcmd:` 64 KB chunks; ≤ 64 entries, least recently used
  evicted; ≤ 8 s of audio). When the voice changes (owner setting, the box connects or goes away)
  every cached text and every agent's phrase is re-synthesised in the background. A miss
  (evicted, a new voice) synthesises once at play time, then it is cached.
- **`quick {id, in_reply_to?, force?}`** (relay command, `POST …/cmd`, MCP `molty_quick`): a
  job of kind `quick`, answered at once `{job, phrase, text, cached}`. It streams the cached
  audio as a say (`cmd say` with the exact `ms`, frames with the cached cues): no TTS call. It
  claims the human's turn like a say. It waits for its `say.done` (the speaker is free), then:
  nothing queued behind it → `mood thinking` (sent before the lock is released, so it can never
  land after the next say). Job result `{phrase, text, ms, cached, timings}`.
- **Lead-ins: one queue.** A draft's opener ([While the human speaks](#while-the-human-speaks)),
  a quick phrase and Molty's own filler are the same thing to the relay: a *lead-in* job owned
  by an agent (the relay, for the filler). While one holds the audio lock, its owner's next
  `say` / `talk` / `quick` — anyone's, behind the filler — is admitted and queued behind it
  (one at a time) instead of `audio_busy`: its job starts at once (its speech is synthesised
  while the lead-in plays) and it gets the lock — then sends `cmd say` — the moment the
  lead-in's `say.done` arrives. The gap is one device round trip, no synthesis. Another agent
  still gets `audio_busy` (or `turn_claimed`). All three play pre-synthesised speech through the
  same path (`prepareSpeech`): a quick from the phrase cache, an opener from the cache when its
  text is a cached phrase (else synthesised while the human talks). A played opener counts as
  its agent answering: no auto filler for that turn.
- **Turn trace.** An agent's quick answering a turn is its `reply` (`op: "quick"`); Molty's filler
  is an `ev: "filler"` entry `{job, phrase, text, first_audio_ms, category, classifier, source:
  agent | builtin, owner?}` (`first_audio_ms`: after the human stopped; `owner`: whose fillers).
- **The auto filler.** When a human turn ends with words — a shake's `utterance`, or a talk
  whose listen heard something — and no agent does anything (any job, `mood`, `show`, `act`,
  a state patch, a draft's opener) within the owner's delay counted from the listen's end (the
  end frame, or the box's turn end) — not from when the transcript came back — the
  relay starts a relay-owned quick (no agent, never claims the turn):
  - **Whose:** the fillers (`filler: true`) of the agent that last answered a human turn here
    (the last turn claimer, or the last agent to talk); none → the built-ins; that agent turned
    the built-ins off (`builtins: false`) and has none → no filler at all.
  - **Which:** picked by the category of the human's utterance — `question` → a `for:
    "question"` phrase ("Good question."), `request` → `request` ("On it.", "Checking."), `hard`
    → `hard` ("Let me think."), else (`other`, or nothing made for that category) an `any`
    phrase ("Hmm…", "One sec.", "Let me see."); nothing fits → no filler. Never the same phrase
    twice in a row when another fits.
  - **Classifier:** one path — [Molty's reflex](#reflex) (`DeviceRoom.fillerCategory`): the
    category the reflex already decided for those exact words, else one call of the owner's
    engine (`jev` / `openai` with a key), the keywords engine when the reflex is off or has no
    key. It starts when the turn ends, in parallel with the delay, with `CLASSIFY_BUDGET_MS` (400 ms);
    a throw, an unknown category, the deadline, or a verdict not in by the filler's moment → the
    keywords. Nothing adds to the owner's delay: the filler never waits for the classifier, the
    pool is looked up when armed, the audio comes from the phrase cache (warmed during the listen).
    A delay shorter than the STT's own latency fires as soon as the words are in. `RoomDeps.classifier`
    (`UtteranceClassifier {name, classify(text)}`, `services/relay/src/core/phrases.ts`) overrides
    it for tests or other hosts. The trace's `classifier` names the engine that decided. Not while anything holds the speaker, the human is talking, a question or an explicit mood is
  in flight, or the device has no speaker. Its audio is warmed during the listen. After it,
  `thinking` again (unless the turn's `ack` was off). An agent's `quick` within 30 s of it with
  nothing else from that agent since is skipped: `{skipped:"filled", filler:{phrase, text,
  ms_ago}}` (`force:true` plays it anyway). Recorded in the activity log as a `quick` job with
  `data.filler:true` and `data.turn` (owner view; no agent).
- **Delay setting.** The owner's choice, console Settings › Molty "filler" (`POST
  /api/creature/state {filler_ms}`: `0` = off or 400..5000 — chips off / 0.5 / 0.8 / 1.5 / 2.5 /
  3.5 s —, GET reports it, NVS like
  `ring_color`; `link_filler_setting_ok`); every listen answer reports it (`filler_ms`).
  Firmware that does not report it: 2500 ms. The `utterance` event and talk's result carry
  `filler_in_ms` (ms from then until the filler; absent = off or nothing heard). A relay older
  than the 400 ms floor reads 400..1499 as not reported (2500).

### Shake to talk

The human shakes Molty and just speaks: no agent round trip before the mic opens (with an agent
woken by a webhook that was ~11–16 s of "Yeah?" first).

```
shake ─▶ device: listening at once (ring + mood), audio kept locally
           └─ evt shake {…, listen:"shake-3"} ─▶ relay: cmd listen {job, adopt:"shake-3", vad:false?}
                                                    └─ device: frames under `job`, from the shake's first sample
            relay: the usual listen job (box streaming STT + semantic end of turn, else cloud / device VAD)
              └─ heard words ─▶ ONE `utterance` event ─▶ every agent (inbox + webhook)
                                  └─ first say / talk claims the turn
```

- **Device** (cap `shake_talk`, boards with a mic and an IMU; console setting "shake to talk",
  `POST /api/creature/state {shake_talk: bool}`, GET reports it, NVS like `ring_color`, on out of
  the box). On a shake (≤ 1 per 2 s) it starts a listen **by itself** — when the setting is on,
  the relay's welcome listed `listen_adopt`, the link is up and nothing else owns the device: no
  say / listen running, no question on screen, no pairing, no update writing. `listening` mood
  and ring at once; window and acknowledgement from the device's settings. It records under a
  local id (`shake-<n>`) and sends `evt shake {peak_g, reversals, ms, listen:"shake-<n>"}`;
  otherwise it sends the plain shake (no `listen`). Nothing goes up until the relay adopts it.
- **Adopt.** The relay answers with `cmd listen {job, adopt, …}` — the same args it sends for an
  agent's listen (`vad:false` with the voice box: semantic end of turn). From then on the listen is
  that job: its frames carry `job`, the relay's end-of-turn rules, window (absent = the device's
  setting, counted from the shake) and `ack` apply as if it had begun with them, and the audio
  recorded so far replays through them and goes up first. A cmd say/listen sent while the shake's
  listen waits is answered `busy` as usual.
- **Declined / unclaimed.** The relay declines (`cmd listen_stop {job:"shake-<n>"}`) when an audio
  job is already running there (a say or listen crossed the shake) or the device has no mic. Not
  adopted within **3 s** of audio (`LINK_SHAKE_ADOPT_MS`), declined, or the link went down: the
  listen ends quietly — no frame, no acknowledgement, `idle`. A late adoption is refused
  `listen_gone`.
- **Agents' shake.** The `shake` event still goes to agents either way; when the relay adopted
  the listen it says so: `{peak_g, reversals, ms, listening: true, turn_id}` (the local id never
  reaches agents). Agents should not react to it: the utterance follows.
- **Utterance.** When the listen ended with words (a non-empty transcript), the relay stores the
  turn and appends ONE `utterance` event (relay-generated, not rate-capped, never accepted from a
  device): `{turn_id, text, reason, ms:{speech, stt}, trigger:"shake", device:{caps, mood, voice}, filler_in_ms?}` (`filler_in_ms`: see [Quick phrases](#quick-phrases-and-the-auto-filler)).
  `turn_id` is the listen job's id (`GET /v1/jobs/<turn_id>` has the full listen result);
  `ms.speech` the measured speech (else the recording's length), `ms.stt` the transcription's
  tail; `device.mood` what Molty shows now (`thinking`: its acknowledgement, unless `ack` is off →
  `idle`), `device.voice` who would speak now (as `status` `relay.voice`). **No speech** (reason
  `no_speech`, or an empty transcript): **no `utterance` at all** — only the shake was sent; the
  device already went back to idle without a chirp. A broken listen (`listen_failed`,
  `device_offline`): no utterance either. The device's turn acknowledgement (chirp + thinking)
  applies as for any listen.
- **Who answers.** All paired agents get the event (routing a gesture to one agent comes later).
  The first `say` or `talk` after it — from any agent, with `in_reply_to: turn_id` or without —
  **claims the turn**; for **60 s** after the utterance (`TURN_HOLD_MS`) every other agent's `say`
  / `talk` is refused `409 turn_claimed {turn_id}` (before, and instead of, `audio_busy`). Only a
  say / talk the relay admits (it got the speaker) claims: one refused `audio_busy` or anything
  else claims nothing, so the turn stays open for the next answer. The
  claimant keeps the floor (follow-ups need no `in_reply_to`); `mood`, `show`, `ask` are never
  claimed. `in_reply_to` naming an older turn (the human has spoken again since) goes ahead
  unclaimed and uncorrelated. With a claimed turn the answer's `timings.turn` is
  `{id, reply, first_audio}`: ms from the utterance to the call and to its first audio.
  `say` / `talk` / `ask` take an optional **`client_timing`**: the agent's own latency for this
  call, in ms — an object of ≤ 8 keys (`[a-z][a-z0-9_]{0,31}`), each a number 0..3600000, e.g.
  `{received_ms, model_ms}` (event received → this call, the model's run); anything else
  `invalid_args`. Relay-only (never sent to Molty): kept in the job's `timings.client` and, for a
  say / talk / ask answering a turn, in that turn's [trace](#turn-trace) (`ev:"reply"`). `ask`
  also takes `in_reply_to` (checked like say / talk's): naming the open turn it is traced as a
  reply (and gets `timings.turn`), but an ask never claims the turn.
- **Shake handling noise** (firmware cap `trace`): the shake itself is loud in the mic. The
  device drops the audio of an adopted shake listen until the IMU shows the shake has settled —
  `| |a| − 1 g | < 0.15 g` for 150 ms, from the mic start, capped at 600 ms — and fades the
  first 10 ms it keeps in; nothing before that point is counted, sent or fed to the VAD. The
  end frame's `tr.set` / `tr.setc` say how much went (boards without an IMU trim nothing).
- **While the human is still talking** the turn is *open*: agents get `utterance.partial`, may
  `draft` an opener and `react` with a mood, and nothing else — [While the human speaks](#while-the-human-speaks).
  Agents should ignore event types they do not know.

### While the human speaks

From the adoption of a shake's listen until its utterance (or its end without one) the human's
turn is **open**. Code: `services/relay/src/core/partials.ts` (chunking, judging),
`core/calibration.ts` (the human's habits), `core/room.ts` "While the human speaks".

```
box stt.partial (each word) ─▶ chunker ─▶ utterance.partial {turn_id, seq, text_so_far, new_text, elapsed_ms} ─▶ every agent
                                  (a sentence end · N new words · T s — whichever first; none before 3 s)
agent: draft {turn_id, based_on, opener, max_new_words?} ─▶ held, its audio synthesised now (cached)
agent: react {turn_id, mood|action}                        ─▶ mood {react:true} (back to listening) | act {action}
agent: say / talk / ask / mood / act / show / listen / state ─▶ 409 human_speaking {turn_id}
turn end ─▶ judge drafts ─┬─ holds: opener plays at once (after the chirp), claims the turn ─▶ draft.used (to it)
                          └─ else ─▶ draft.dropped {reason} (to it) — today's path
          ─▶ ONE utterance (claimed: true when an opener plays)
```

- **Partials** (`utterance.partial`, relay-generated, every agent's inbox): only with the voice
  box (its streaming STT sends the text so far on every word; the cloud path has none). Chunked
  by meaning, never token by token: one goes out when the text so far ends a sentence (Kyutai
  punctuation; not an ellipsis), or `every_words` new words arrived, or `every_ms` passed since
  the last one with a new word waiting — whichever first — and never before the turn ran
  `lead_ms` (3 s: a shorter turn gets none), at most 8 per turn. `seq` counts from 1 per turn;
  `text_so_far` is all heard so far (an STT revision counts new words from where the texts
  differ), `new_text` what this one adds, `elapsed_ms` since the adoption. Webhooks get them
  only when their `events` names `utterance.partial` (never by default: chatty); pull and
  ride-along carry them.
- **human_speaking.** While the turn is open the relay refuses every agent's `say`, `talk`,
  `ask`, `mood`, `act`, `show`, `listen` and patching `state` with `409 human_speaking {turn_id}` (before
  `turn_claimed` / `audio_busy`; nothing reaches the device). Reads (`status`, `state` without a
  patch, `diag`, …) go through. The turn closes however its listen ends (a box failure, the device
  dropping: drafts are dropped `turn_failed`).
- **`draft {turn_id, based_on, opener, max_new_words?, voice?}`** (`POST /v1/devices/<id>/draft`,
  MCP `molty_draft`): `based_on` the `seq` of one of this turn's partials, `opener` ≤ 200 bytes and
  ≤ 24 words, `max_new_words` 0..20 — capped by the relay's calibrated threshold (default 4),
  which is also the default. Held silently; its audio is synthesised at once (the TTS the next say
  would use) and kept until the turn ends. One per agent per turn: a new one replaces it (the old
  one `draft.dropped {reason:"replaced"}`; re-based with the same `opener` and `voice`, its audio is
  kept, not synthesised again), at most 3 made (`429 rate_limited`). The turn not open
  (any more): `409 turn_closed`. → `{turn_id, based_on, status:"held", max_new_words, threshold}`.
- **At the turn's end** (`judgeDraft`), drafts in the order they were made: the final transcript
  must still begin with `based_on`'s text (one revised last word tolerated; else `revised`), none
  of the words it adds may be a turn-around word (`but`, `not`, `no`, `never`, `actually`,
  `instead`, `wait`, `cancel`, `except`, `unless`, `don't`, … `FLIP_WORDS`; else `meaning`), and it
  may add at most the draft's `max_new_words` (else `new_words`). The first that holds wins —
  later holding drafts are `turn_claimed` — if its synthesis did not fail (`synth_failed`). Nobody
  spoke: `no_speech`, a broken listen: `turn_failed`.
- **The winner**: the turn record is written claimed by its agent (the `turn_claimed` rules of
  [Shake to talk](#shake-to-talk) apply from here), the listen hands its audio lock straight to a
  `say` job of the cached opener (no other call can slip in; its `cmd say` goes out before the turn
  record is written, the turn staying open meanwhile), and the device plays it at once —
  its `cmd say` arrives while the ack chirp plays and starts when the chirp ends. Then
  `draft.used {turn_id, based_on, opener, new_words, job}` to that agent only, before the
  `utterance` (which says `claimed: true`). That agent's next `say` / `talk` (with `in_reply_to` or
  without) **queues behind the opener**: a `queued` job whose speech is synthesised meanwhile and
  whose `cmd say` goes out the moment the opener's `say.done` arrives. Other agents: `turn_claimed`.
- **Dropped drafts**: `draft.dropped {turn_id, based_on, reason, new_words?}` to their agent only,
  their synthesis stopped; the utterance goes out unclaimed — today's path.
- **`react {turn_id, mood}` or `{turn_id, action}`** (`POST /v1/devices/<id>/react`, MCP
  `molty_react`): `mood` one of `happy`, `surprised`, `thinking` (`REACT_MOODS`), or `action` one of
  the device's gestures (`REACT_ACTIONS` = `ACTIONS`, the list of `act` and inline cues). Screen
  only — no sound while the mic is open. An action is the device's `cmd act {action}` (cap `act`:
  a one-shot gesture that never takes the screen from the listen). The relay sends `cmd mood {mood, hold_s:0, react:true}` and, after
  1.5 s, `mood {mood:"listening", hold_s:0, react:true}` unless the listen ended meanwhile. The
  firmware (cap `react`) shows a react mood without counting it as an explicit one: the listen's
  end still acknowledges the turn (chirp + thinking) and falls back to idle, and a pending
  question stays up. Without the cap: `409 unsupported` (a plain mood would cancel the
  acknowledgement). At most one per 3 s per Molty (`429 rate_limited {retry_after_ms}`).
- **In the turn trace** ([Turn trace](#turn-trace), `relay`): `partials` `[[seq, ms, words], …]`,
  `drafts` `[[based_on, ms], …]`, `reacts` `[[mood|action, ms, "ok"|error], …]` (ms from the
  trace's t0; counts only, never words), `draft` `{used?: based_on, new_words?, opener_at?,
  dropped?: [reasons]}` and `utterance` (when it went out).
- **Targeted events.** `draft.used` / `draft.dropped` are stored with their recipient (never
  returned): only that token's pull / ride-along / webhook sees them.

### Reflex

Molty reacts by itself to **what** the human says while they talk — with any agent, also one that
never reads partials. An owner setting (`reflex` in the [voice owner API](#owner-api-console),
the console's Voice card; default `off`). Code: `services/relay/src/core/reflex.ts`, room.ts
"Molty's reflex", `services/molty-voice/molty_voice/reflex.py`.

```
box stt.partial ─▶ reflex chunk n ─▶ engine ─▶ pick + category ─▶ liveliness gate ─▶ fire gates ─▶ mood {react:true} | act
                   (3 words, then     local:    the box's classifier, stt.reflex {n,…}       full / soft / none
                    every few words,  jev:      TypeSafe System One (TYPESAFE_API_KEY)
                    a sentence end    openai:   OpenAI Decisions, gpt-6-luna (OPENAI_API_KEY)
                    or ~1.2–2.5 s;    keywords: relay heuristic, no key
                    ≤ 40)             error / no answer in 600 ms ─▶ keywords' pick instead (never blocks the listen)
```

- **When**: on every listen the voice box streams (shake turns and agents' listens). The first
  chunk is the text so far at 3 words (mid-sentence: a short turn gets its reaction while it is
  still being spoken); then, with a new word, once the liveliness's `every_words` new words came,
  the text ends a sentence, or its `every_ms` passed since the last chunk; at most 40 per listen
  (`reflexDue`). At most 2 calls of a remote engine are in flight (a chunk due beyond that waits
  for the next word); a verdict landing after a newer chunk's is `stale` (noted, never shown).
  The box classifies every word count from 3 on (~35 ms of CPU each, at most 120 per listen),
  so whichever the relay picks has its verdict.
- **Liveliness** (owner setting `liveliness` = `calm | normal | lively`, default `normal`; the
  console's Voice card; `REFLEX_LIVELINESS`):

  | | every | gap (any react / reflex) | full pick at (local / jev, openai) | mild pick |
  |---|---|---|---|---|
  | calm | 6 words or 2.5 s | 3 s | 0.35 / 0.5 | — |
  | normal | 4 words or 1.5 s | 2 s | 0.3 / 0.4 | `none` < 0.6 and a reaction ≥ 0.3 |
  | lively | 3 words or 1.2 s | 1.5 s | 0.25 / 0.35 | `none` < 0.75 and a reaction ≥ 0.2 |

  A **mild** pick shows as that reaction's softer gesture (`act`): surprised → `look_up`, happy →
  `wiggle`, sad → `nod`, laugh → `wobble`, curious → `glance_left` / `glance_right` (alternating).
  A request is never curiosity, in full or mild. Tuned with `molty-sim reflex-turns` /
  `reflex-bench` (tools/sim/README.md).
- **Engines** (`reflex` = `off | auto | local | jev | openai | keywords`; `auto` = local when the
  box serves the listen and offers its classifier, else jev with a key, else keywords). Each
  answers a reaction (`surprised happy sad laugh curious none`) and, in the same call, the
  utterance **category** (`question request hard other`, for context-picked fillers). The model
  engines see the last 400 characters of the text so far. A pick below its engine's gate at the
  liveliness is `none` (or mild, above). A chosen engine that cannot run (no key, no box
  classifier) answers with the keywords, saying why (`fallback`); one refused for good
  (HTTP 400/401/403/404) is benched for 10 min.
- **Shown** through the react path, screen only: surprised / happy → `mood {mood, hold_s:0,
  react:true}` (cap `react`; back to `listening` after 1.5 s), sad → `act nod`, laugh → `act
  bounce`, curious → `act peek` (cap `act`); a mild pick → its soft gesture. Not fired (and noted
  why): the listen ended (`closed`), an owner screen is up — a pending question, a pairing code,
  an update (`screen`) —, an agent reacted this turn or within the gap (`agent`: **agents' reacts
  win**, the reflex never limits theirs), another reflex within the gap (`rate_limited`), a newer
  chunk already answered (`stale`), the firmware lacks the cap (`unsupported`).
- **On the device**: a react mood or an `act` during the listen tells the listen it plays
  (`LINK_REACT_SHOW_MS` / the gesture's length): the firmware's own listener reactions
  (`listen_react.h`: the pause nod, the question glance, the perk, the baseline) wait for it, so
  a reflex is never cut short. Between reactions Molty keeps an **attentive baseline** while a voice
  is heard: a micro-motion (blink, glance left, blink, glance right, …) on a dip of the voice once
  nothing moved it for 2.5 s (calm idle life: 5 s; off: none).
- **Compare** (`reflex_compare: true`): every available engine runs on each chunk, in parallel;
  only the chosen one fires. All decisions go in the turn trace.
- **Turn trace** (`relay.reflex_cfg {mode, engine, lv, fb?, compare?}`, `relay.reflex [{n, at, e,
  ms, ch, tk?, pick, raw?, soft?, c?, p?, cat?, cc?, fired?, fb?, err?, late?}]`): per decision the
  chunk (`n` words), when (ms from t0), the engine, its latency, input characters and tokens, the
  pick (and the engine's own choice when the gate changed it; `soft` for a mild one), confidence, probabilities in the order above, the category,
  whether and how it fired, the fallback reason, the error. Never words. Capped: probabilities
  go first, then all but the newest 12 decisions.
- **Keys**: Worker secrets (`wrangler secret put TYPESAFE_API_KEY`, `… OPENAI_API_KEY`), never
  logged or traced; errors are codes (`timeout`, `http_401`, `network`, …).
- **Fillers**: `DeviceRoom.fillerCategory(text)` gives the category of the latest partial / final
  text — the reflex's own answer for those words when it has one, else one call of the owner's
  engine (keywords when off or failing).

### Calibration

The relay keeps one record per Molty of how its human talks (KV `speech`,
`services/relay/src/core/calibration.ts`), from every heard listen (shake turns and agents'
listens): words, length (the measured speech, else the recording), and pauses (gaps ≥ 600 ms
between the box's word arrivals); the last 50 turns. And every draft's outcome (the last 30).

- **Partial policy** for the next turn: the defaults (`every_words` 8, `every_ms` 4000) until 8
  turns are in; then `every_words` = median words / 3 (4..20) and `every_ms` = median length / 3
  (2..8 s), so a typical turn gets partials at about 1/3 and 2/3, then its utterance. `lead_ms`
  stays 3 s: a turn predicted shorter gets none.
- **Draft threshold** (the most words a draft survives), 1..10, starts at 4. After every 6 judged
  outcomes (`used`, `misfire`, `new_words`, `meaning`) it moves one step on the last 20: more
  than 25 % of the spoken openers were misfires → −1; more than 40 % of judged drafts died of
  `new_words` while misfires stay ≤ 10 % → +1. A **misfire** is a shake while an opener (or its
  queued follow-up) plays or within 2 s after the opener ended: the human cut in.
- **Visible** to the owner: `GET /v1/devices/<id>/speech` (link-code auth + CORS, like the
  [voice owner API](#owner-api-console)) → `{turns:{sampled, total, needed}, words, seconds
  {median, p25, p75}, wpm, pauses:{per_turn, max_ms}, policy, drafts:{made, used, misfires,
  dropped, use_rate, misfire_rate, threshold, threshold_bounds}, partials, reacts, updated}`;
  `DELETE` resets it. The console's activity page shows it as the **speech habits** card. A
  changed policy or threshold is a `settings` / `calibration` entry in the [activity log](#activity-log).

### Notes

A small private key-value store per agent token (`services/relay/src/core/notes.ts`), so an agent
without memory of its own can keep its behaviour ledger (what it tried through Molty and how the
human responded). `GET /v1/notes` (list: `{keys:[{key, bytes, updated}], bytes, limits}`),
`GET /v1/notes?key=k` (`{key, value, updated}`; `value: null` when unset), `PUT /v1/notes {key,
value}`, `DELETE /v1/notes?key=k`; MCP `molty_notes {action: list|get|put|delete, key?, value?}`.
Keys 1..64 of `[A-Za-z0-9._:-]`; values any JSON, ≤ 8 KB each, ≤ 64 keys and ≤ 32 KB per token
(`413 too_large`, checked in one atomic read-check-write). One document per token (`note:<token
hash>`): no other token reads or writes it; revoking the token or forgetting the device deletes
it. The activity log records the op and the key, never the value.

### Listen end of speech (device VAD)

`device/firmware/main/audio/vad.h` — energy VAD on the 16 kHz mic stream (the board's mic gain:
`mic_gain` in `molty_board_t`, 6 on the 1.46 — lowered from 8 after a real clip saturated
18 samples at 8; 8 when a board leaves it 0), 20 ms
frames, RMS in dBFS against an adaptive noise floor:

- **Floor**: minimum frame energy over the last 3 s. The first 300 ms only measure it; the
  moment it exists those frames are classified retroactively, so a short reply said right at
  the start ("yes" inside the first 300 ms) still counts as speech. Drops at once to a quieter frame; a steady fan becomes the floor after
  ≤ 3 s. Until 3 s have passed it is capped at −50 dBFS, so speech already running
  when `listen` starts is not mistaken for the floor.
- **Speech**: energy > floor + 10 dB, or > floor + 5 dB while already speaking
  (hysteresis: a softer tail stays speech); never below −60 dBFS.
- **Ends** at the first of: ≥ 160 ms of speech, then `end_silence_ms` of continuous
  non-speech (never before 600 ms) → `silence`; `no_speech_ms` with < 160 ms of speech
  and nobody speaking right then → `no_speech`; `ms` → `max`. The mic stops at once.

**Semantic end of turn is the default with a voice box.** When the owner's [voice box](#voice-box)
serves the listen (it is picked for STT and its stream opened) and the firmware lists
`listen_stop`, the relay sends the device listen with `vad:false`: the box's end of turn
(`stt.turn_end`, Kyutai's pause prediction) is THE end, and the box also ends a listen nobody
spoke in (`no_speech_ms`, passed in `stt.start`: the agent's, else 8000 →
`reason:"no_speech"`, `heard:""`, no transcription). The box decides "nobody spoke" from voice
activity in the captured audio (the model's own speaking estimate, plus a frame-energy veto
near the deadline), not from words, which lag the voice by ~1–1.6 s; any activity restarts
its clock. The device's silence VAD stays off because
it heard Molty's own speech tail and cut humans off. Agents need not pass anything. An agent
that passes `vad` or `end_silence_ms` keeps the device VAD as asked; the cloud path, a box that
could not open, and firmware without `listen_stop` keep the device VAD as before. A box that
drops mid-listen while the device VAD is off ends the listen at once (`reason:"error"`, what
was said is transcribed — by the cloud in `auto` mode) instead of running out the window.
A listen that breaks on the device's side is an error, never `no_speech` or an empty result:
the device's end frame with `reason:"error"` (its capture failed) → `listen_failed`; the
device's link dropping mid-listen → `device_offline`.

Optional `listen` args (validated by the relay and again by the device; forwarded only when the agent gives them):

| arg | range | default | |
|---|---|---|---|
| `end_silence_ms` | 300..3000 (integer) | 700 | silence after speech that ends the listen; raise it for slow / hesitant speakers |
| `no_speech_ms` | 1000..10000 (integer) | 4000 (device VAD); 8000 when the voice box decides | give up when nobody spoke by then (≥ `ms` = never) |
| `vad` | bool | `true` (off with a voice box, see below) | `false`: record the full `ms` window as before |
| `ring_color` | a colour name or `#rrggbb` | the device's setting | the listening ring's colour for this listen (also on `talk`) |
| `ack` | `true`, `false`, `"silent"` | `true` (the device's setting) | the device's own [turn acknowledgement](#turn-acknowledgement): `"silent"` = no chirp, `false` = none (also on `talk`) |

Out-of-range or mistyped values → `invalid_args`.

Moods (`mood` cmd, and the implicit `listening`/`speaking` around audio jobs) are moods
of the fluid creature's loaded `.molty` creature: the device applies
`{"state":"creature","mood":"<mood>"[,"hold_s":N]}` (blob when no creature is loaded).
During `say` the text state wins over the creature view.

What the screen does between commands (`device/firmware/main/fluid/fluid_director.h`):

- **The creature is home.** The device boots into it, and re-sending the state or mood it
  already shows changes nothing: a mood blends inside the creature instead of melting it
  and re-forming. The demo reel runs only on an explicit `state:"autoplay"` (never
  saved; pairing and the Improv "hi" go back to the creature, not the reel).
- **Quick moods revert.** `happy` (3 s) and `surprised` (2 s) return to `idle` on their
  own; `listening`, `thinking`, `speaking`, `sleepy` persist until the next mood.
  `hold_s` overrides either (`0` = until the next mood).
- **`show` returns** to the creature 1.5 s after its last word; `say` ends in `idle`.
- **Idle life.** While idle, the creature blinks, glances and breathes, and every
  20–60 s flashes a short `happy` or `surprised`. After 5 minutes without a touch or a
  command it dozes off (`sleepy`, 20 fps); a touch, a button, a shake or any command
  wakes it. `status` reports the mood on screen.
- **Status mark.** No Wi-Fi (a short arc), relay offline (a dim dot) or a refused device
  key (an accent dot) shows as a small mark at the bottom edge after 10 s; it never
  changes the state. Only the pairing code takes over the screen.

still the plain string. The self-update question is fixed: the version (`v0.2.0`) green, `later` white.

Agent-facing calls are **async-friendly** (agent runtimes commonly cap a tool call at ~10 s / 64 KiB):

24 s (under common ~30 s MCP tool timeouts) and otherwise return `{job, status:"pending"}`.

last frame), `play` (first frame → playback end / `say.done`); listen: `cmd` (listen ack),
`record` (ack → end frame), `first_frame`, `stt`; `total`.

### Inline cues and actions

Molty is not "always idle": agents add expression without extra calls, and the creature has an
idle life of its own.

**Inline cues** (relay: `parseCues`, `services/relay/src/core/speech.ts`). The text of `say`,
`talk`'s `say` and `ask`'s `say` may carry `[name]` cues:
`"[happy] Build passed! [thinking] Three tests were flaky… [surprised] wait, one is new."`

- A cue is `[` + 1..24 characters without `[`, `]`, CR or LF + `]`. Its name is the inside
  trimmed, lower-cased, runs of spaces / tabs / hyphens → `_` (`[Shake Head]` = `shake_head`).
  A mood (`MOODS`) or an action (`ACTIONS`, `commands.ts`) becomes a **mark**; any other name is
  stripped silently. An unescaped `[` or `]` that forms no cue is dropped silently too.
- `\[` and `\]` are literal brackets (spoken and shown); any other backslash is literal.
- Cues are **never spoken and never shown**: TTS, `cmd say`'s `text`, the word cues and the
  job's `text` / `said` all use the stripped text. Removing a cue never doubles a space; the
  result is trimmed. Nothing left to speak → `invalid_args` (use `mood` / `act`). The 4096-byte
  limit applies to the text as sent.
- A mark's word = the words of the stripped text (counted like the reader) that start before
  the cue: a cue before word k fires with word k, mid-word with the next word, after the last
  word when the speech ends. At most 16 marks (the rest dropped), exact duplicates dropped.
- Timing is the say's word-cue path: the device fires a mark the moment its word is revealed,
  i.e. with the voice box's own word timing or the cloud's per-character estimate.
- Firmware without `say_marks`: the cues are still stripped, nothing fires.

**On the device** (`link_audio.c`, `mole_fluid.c`, `fluid_director.c`):

- During a say the words cover the creature. A **mood mark** tints the words from its word on
  (happy amber, surprised cyan, thinking violet, sleepy blue, listening green; idle / speaking
  the palette's colours) and becomes the creature's mood when the say ends — instead of `idle`,
  unless an explicit `mood` arrived during the say (it wins, as ever); happy / surprised / idle
  keep their default hold, the others hold 8 s. An **action mark** asks the creature for that
  action: it plays once the creature is back (within 3 s, else dropped), so trailing actions
  (`"Done. [nod]"`) land as the words melt.
- Marks never take the screen: none fires while a question, a pairing or an update owns it,
  they never cancel a question, and they are not explicit moods (`link_cmd_mood_gen`).
- **`act {action}`**: the same action, any time. It plays over the current mood (an additive
  pose layer, `device/firmware/main/creature/cute_act.h`; JS twin `device/creatures/js/actions.js`,
  pinned sample for sample by `test/host/act_golden.txt`); a newer one replaces it (0.25 s
  fade). It never changes the state or mood, never cancels a question, never makes a sound;
  while words or a question cover the creature it waits up to 3 s, then is dropped. A sleeping
  creature wakes for it. Local twin: `POST /api/creature/state {act: "nod"}`; GET reports the
  action playing as `act`.

**Idle life** (`fluid_director.h`). With nobody driving it, the creature plays one small action
from a weighted library every 10–40 s — glance left / right, blink (×3 weight), look up (×2),
wobble, stretch (×1.5) — never the same one twice in a row; "calm" keeps the small ones every
20–60 s; "off" plays none. Only while the creature is on screen, in `idle`, awake, and nothing
owns the screen: never during a say, a listen, a question, an update or pairing screen, the
turn acknowledgement's `thinking` or any agent mood. After 5 min without touch or agent activity
it **yawns**, then dozes off (`sleepy`; off: no yawn). A say that played to its end, the
creature back and idle within 8 s: one `happy` flash (at most one a minute). The console's
setting: Settings › Molty "idle life" (`POST /api/creature/state {idle_life:
"lively"|"calm"|"off"}`, GET reports it, kept in NVS like `ring_color`; lively out of the box).
**Frame cost:** the action layer is a handful of `sinf` per frame on the creature's pose
(host: within ±0.03 µs, i.e. noise, of a ~54 µs creature update + raster + fill — scaled to
the device's ~11 ms creature work, a few µs of a 33 ms frame), the scheduler a few
comparisons: no measurable change to the ~30 fps. Not yet measured on hardware.

## Device events

Device→relay `{"t":"evt","name":...,"data":{...}}` frames, sent only while the link is up
(not queued) and never while a pairing is pending (its tap and buttons decide the
pairing). Rate-limited on the device. `shake`, `tap` and `button` reach agents through the relay's inbox ([Events](#events-device--agents)).

| name | data | when |
|---|---|---|
| `say.done` | `{job}` | a `say` finished playing (its last PCM left the speaker) |
| `shake` | `{peak_g, reversals, ms, listen?}` | the board was shaken (boards with an IMU): ≥ 3 sign reversals of > 1.2 g dynamic acceleration on one axis within 800 ms; ≤ 1 per 2 s. `peak_g` largest dynamic acceleration (g), `ms` first peak → detection; `listen` the local id of the listen it started ([Shake to talk](#shake-to-talk)) |
| `tap` | `{x, y}` | a finger touched the screen (boards with touch); 0..1 of the panel from the top left; ≤ 4/s |
| `double_tap` | `{x, y}` | two taps within 350 ms, when bound to `event` (out of the box a double tap talks) |
| `button` | `{id: "accept"\|"reject"}` | a button was pressed (the board's accept / reject buttons); ≤ 4/s. For agents it means acknowledge / dismiss, never an answer (answers come only from `ask`) |
| `answer` | `{job, index, label}` · `{job, index: null, reason: "timeout"\|"cancelled"}` | an `ask` ended: tapped (0-based `index`, `label` verbatim), timed out, or cancelled; one per job, never rate-limited |

The device reacts to a shake by itself (a brief `surprised`), agent or not. While a `listen`
records, a thin line of the fluid itself condenses just inside the screen's rim around Molty
(in its `listening` mood, in the middle) and breathes: the whole circle expands and
contracts, calm while the room is quiet, quicker and deeper as the human speaks (the mic level,
~10 Hz, smoothed), and circular ripples run inward across the fluid from the whole rim; silence
settles it back to a calm breath, nothing ever travels around it
(`mole_fluid_listen`, `fluid_target_ring`; every tuning knob in
`device/firmware/main/fluid/fluid_ring.h`). It is never shown over a pending `ask`. Its colour:
the listen's `ring_color`, else the device default (console setting, NVS), else the palette's
accent (mono palettes always show their accent). Detector
constants: `device/firmware/main/sense/gesture.h`.

## Events (device → agents)

Molty is not only driven; it reports what its human does to it. Agent-visible events
travel device → relay → each paired agent's own inbox → the agent, by whichever receive
mode suits that agent.

```
device evt ──WSS──▶ DeviceRoom.onEvt
                     ├─ allow-list + shape check (shake, tap, button, answer; rest stays internal)
                     │    (+ relay-generated: utterance, utterance.partial, draft.used / draft.dropped to one agent)
                     ├─ cap 30/min/device (excess dropped, counted)
                     └─ ev:<seq> ring (200 / 24 h, DO storage)
                          │  one read cursor per agent token (cur:<token hash>)
                          ├─▶ ride-along: unread `events` on every authenticated response
                          │      (+ one-time `firmware_update`, see "Firmware updates")
                          ├─▶ pull: GET /v1/devices/<id>/events · molty_events (long-poll)
                          │      └─▶ `molty events [--exec cmd]` (CLI, JSON lines)
                          └─▶ webhook: whq:<token hash>:<seq> ─DO alarm─▶ agent-defined HTTPS request
```

### Firmware contract

`{"t":"evt","name":<type>,"data":{…}}`. Only these reach agents; anything else (`say.done`,
`link_code`, …) is relay-internal. An event whose data does not match is dropped.

| type | data |
|---|---|
| `shake` | `{peak_g: number 0..64, reversals: int, ms: int, listen?: string}` → agents get `{peak_g, reversals, ms}` plus `listening: true, turn_id` when the relay adopted `listen` |
| `tap` | `{x: 0..1, y: 0..1}` (screen position, unit square) |
| `button` | `{id: "accept" \| "reject"}` |
| `answer` | `{job, index: int 0..4 \| null, label?: string, reason?: "timeout" \| "cancelled"}`, checked against the pending ask (see the `ask` wire bullet) |

The relay stores `{id:"e<seq>", type, ts:<relay unix ms>, data}`; `seq` increases per device.
`answer` is stored once per ended ask as `{job, index, label|null, reason?}` (`reason` also
`offline` when the relay resolved it because the device dropped, or `timeout` when the device never
reported), appended before the job's result is published, so the asking call's own ride-along
carries it. Answers are not counted against the per-device rate cap (one per ask).
`utterance` ([Shake to talk](#shake-to-talk)), `utterance.partial`, `draft.used` and `draft.dropped`
([While the human speaks](#while-the-human-speaks)) are relay-generated: a device frame with one of
those names is dropped; agents receive and filter them like the device events (the draft events
reach only the agent that drafted).

### Inbox and cursor

- Ring: the last **200** events, none older than **24 h** (trimmed on append, also in DO
  storage so it survives hibernation and eviction).
- Intake cap: **30 events/min per device**; the excess is dropped (counted in storage).
- Each agent token has a cursor. A newly paired agent starts at the head (no backlog).
  Ride-along and pull advance only that agent's cursor, so two agents each get every
  event once. The cursor moves only when events are actually handed over: error responses
  carry no events and move nothing (a failed `molty_wait` job included).
- Webhook acknowledgements are **separate** from the cursor: a delivered event stays
  readable by pull and ride-along, so an event whose delivery exhausted its retries is
  never lost. An agent using a webhook plus another mode sees events twice; dedupe by `id`
  (ids are stable).
- Long-poll admission: at most **2** concurrent waits (`wait_s > 0`) per agent token and
  **16** per device; more answer `too_many_polls` (REST 429). Immediate reads (`wait_s=0`)
  are not counted.

### Receive modes

| Mode | Call | Notes |
|---|---|---|
| Ride-along | any authenticated REST response / MCP tool result | REST: additive top-level `events` (+ `more_events`). MCP: `events` in `structuredContent` and a second text item `Molty: was shaken (peak 2.4 g) 2 min ago [e42].` At most 10 per response; no unread events = the response is unchanged |
| Pull | `GET /v1/devices/<id>/events[?since=e41][&wait_s=0..25]` · MCP `molty_events {since?, wait_s? 0..8}` | `{ok:true, events:[…], next:"e42", more}`, oldest first, ≤ 50. Default `since` = cursor; long-poll returns as soon as an event lands. An explicit `since` never moves the cursor backwards |
| Webhook | `PUT /v1/webhook` · `GET` · `DELETE` · MCP `molty_webhook` | per-agent HTTPS request, see below |
| Stream | `molty events [--n N] [--exec CMD]` | CLI loop over the pull call ([CLI.md](CLI.md#events-and-receiving)) |

Nothing can wake an agent that has neither a reachable endpoint nor a running process; such
an agent sees events the next time it calls anything (ride-along).

### Webhooks

`PUT /v1/webhook` (or `molty_webhook`), body:

```
{"url": "https://…", "method"?: "POST"|"GET"|"PUT"|"PATCH",
 "headers"?: {"Authorization": "Bearer …"}, "body"?: "<template>", "content_type"?: "application/json",
 "events"?: ["shake", "tap", "button", "answer", "utterance", "utterance.partial", "draft.used", "draft.dropped"]}
```

- Placeholders in `url` (URL-encoded) and `body`: `{{event.type}}` `{{event.id}}` `{{event.ts}}`
  `{{event.data}}` (JSON) `{{event.data.<field>}}` (nested up to 3 deep, own fields only:
  `{{event.data.ms.speech}}`, `{{event.data.device.mood}}`) `{{device}}` `{{text}}` (a short sentence:
  "Molty was shaken (peak 2.4 g)", "Molty's screen was tapped", "Molty's accept button was
  pressed", "Molty's question was answered: yes", "Molty's question got no answer (timeout)",
  `The human said to Molty: "…"`). With a JSON `content_type` strings are JSON-escaped (write them inside quotes;
  write `{{event.data}}` and numeric fields unquoted); with
  `application/x-www-form-urlencoded` they are form-encoded; otherwise inserted raw.
  Unknown placeholders are rejected. A missing field renders its default when written
  `{{event.data.peak_g|0}}` (the default is literal text, escaped like a string), else
  `null` in a JSON body and empty elsewhere — so `"peak": {{event.data.peak_g}}` stays valid
  JSON for a tap.
- `events` (optional) limits which event types are sent; default all but `utterance.partial`,
  which a webhook gets only when `events` names it (it is chatty). A conversational agent
  wants `["utterance"]`: the payload is self-contained — `{{event.data.text}}` (the words),
  `{{event.data.turn_id}}` (for `in_reply_to`), `{{event.data.reason}}`, `{{event.data.ms.speech}}`,
  `{{event.data.ms.stt}}`, `{{event.data.trigger}}`, `{{event.data.device.mood}}`,
  `{{event.data.device.voice}}`, `{{event.data.device.caps}}` (JSON) — so it can answer with no
  confirming `events` call, e.g. body
  `{"message": "Molty heard: \"{{event.data.text}}\" — answer with molty_talk {say, in_reply_to: \"{{event.data.turn_id}}\"}"}`.
- No `body`: the relay's own `{"device":"molty-…","event":{id,type,ts,data}}`, `application/json`.
- Every request carries `Molty-Signature: t=<unix ms>,v2=<hex hmac_sha256(secret, S)>` with
  `S = t + "\n" + METHOD + "\n" + path?query + "\n" + body` (GET: empty body). v2 covers the
  request target because placeholders may put event data in the URL; signing only the body
  would let anyone holding one signed GET swap its query within the freshness window.
  `path?query` is the request target exactly as sent on the wire (percent-encoded, as in the
  HTTP request line). The relay canonicalizes the outgoing URL before both sending and
  signing: a fragment and a bare trailing `?` (empty query, including one left by an empty
  placeholder) are dropped, so the target is always `pathname + search`.
  Harmless for targets that ignore it.
- Registration validates and **dry-runs** the template against a sample of every event type
  it will receive (all, or `events`), checks every rendered host, and returns
  `{webhook, secret, dry_run}` (the dry run shown is the first type's). `secret` is shown once (re-registering rotates it and
  re-enables a disabled webhook). Header values, the secret and the URL path/query (often a
  bot token) are never echoed again: `status`/`GET` show `{url: origin + "/…", method,
  headers: [names], events, active, consecutive_failures, disabled?, last_ok_at?, last_error?}`,
  as `relay.webhook` in `status` too. Logs carry the origin only. The dry run echoes the
  rendered body, so keep secrets in headers or the URL. Each token keeps a webhook
  revision (+1 on every register and delete). A registration remembers the revision it
  started from and, after its DNS checks, compares and writes in one atomic step: if the
  token was revoked meanwhile it fails `unauthorized`; if any other register or delete
  happened meanwhile it fails `conflict` (409) — of two concurrent registrations exactly one
  succeeds, and a returned secret always matches the stored webhook.
- `last_error` (and the log line) is a fixed category, never exception text: `timeout`,
  `dns_failed`, `blocked_address`, `blocked_url`, `render_failed`, `network_error`, `http_<status>`.
- Limits: url ≤ 2048 B, body template ≤ 4096 B, ≤ 16 headers / 4096 B; reserved headers
  (`Host`, `Content-Length`, `Molty-Signature`, …) refused; `Content-Type` comes from `content_type`.
- Delivery: queued in DO storage, sent from the DO alarm. One **5 s deadline** covers DNS
  resolution and the request (both aborted on expiry). Registration has one 5 s deadline over
  all of its DNS checks, resolving each host once. Redirects are not followed (a 3xx is a failure), 2xx = success. Retries after
  1 s, 10 s, 60 s, then that delivery is dropped (the event stays in the inbox). Delivery
  stats are written atomically and only onto the webhook they belong to, so a revoke or a
  new registration during an in-flight delivery is never undone.
  **20 consecutive failed attempts disable the webhook.**
- SSRF guard: `https:` only; no credentials in the URL; no IP literals (v4, v6, hex/decimal
  forms); no `localhost`, single-label names or `.local`/`.localhost`/`.internal`/`.lan`/
  `.home`/`.home.arpa`/`.corp`/`.intranet`/`.localdomain`. The rendered host is resolved
  (A + AAAA over DNS-over-HTTPS on Workers) at registration and before every delivery and
  refused if any address is private, loopback, link-local, CGNAT, multicast, documentation
  or otherwise reserved. Addresses are parsed to bytes (any IPv6 spelling or compression);
  IPv6 must be global unicast (`2000::/3`) outside the special blocks, and IPv4 embedded in
  IPv6 (mapped `::ffff:0:0/96`, compatible `::/96`, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`)
  is classified as IPv4; Teredo and the rest of `2001::/23` are refused; unparsable answers
  are refused. **Residual risk, stated plainly:** Workers' `fetch` resolves the
  name again itself, so a DNS-rebinding host could answer differently between our check
  and the request (TOCTOU), and the check trusts the DoH answer. What bounds it: Workers
  egress comes from Cloudflare's network, not from the owner's LAN, so private addresses
  of the owner's home are not reachable from the relay at all; the guard mainly stops
  pointing the relay at Cloudflare-internal or other tenants' private-looking endpoints.

#### Reference verifiers

Pass the request method, the request target as received (path + query, e.g.
`url.pathname + url.search` of the incoming request URL) and the raw body. Reject when the
header is missing, the signature differs, or `t` is outside your tolerance (replay).

<!-- verifier:ts -->
```ts
// Node 20+, Deno, Bun, Workers (Web Crypto). True when the request is authentic and fresh.
export async function verifyMolty(
  secret: string, header: string | null, method: string, target: string, body: string, toleranceMs = 5 * 60 * 1000,
): Promise<boolean> {
  const m = /^t=(\d+),v2=([0-9a-f]{64})$/.exec(header ?? "");
  if (!m || Math.abs(Date.now() - Number(m[1])) > toleranceMs) return false;
  const enc = new TextEncoder();
  const key = await crypto.subtle.importKey("raw", enc.encode(secret), { name: "HMAC", hash: "SHA-256" }, false, ["verify"]);
  const sig = new Uint8Array(m[2].match(/../g)!.map((h) => parseInt(h, 16)));
  const signed = `${m[1]}\n${method.toUpperCase()}\n${target}\n${body}`;
  return crypto.subtle.verify("HMAC", key, sig, enc.encode(signed)); // constant-time
}
```

<!-- verifier:py -->
```python
import hashlib, hmac, time

def verify_molty(secret: str, header: str | None, method: str, target: str, body: bytes, tolerance_s: int = 300) -> bool:
    """True when the request is authentic and fresh. target = path + query as received; body = raw bytes."""
    try:
        parts = dict(p.split("=", 1) for p in (header or "").split(","))
        t, v2 = parts["t"], parts["v2"]
    except (ValueError, KeyError):
        return False
    if not t.isdigit() or abs(time.time() * 1000 - int(t)) > tolerance_s * 1000:
        return False
    signed = f"{t}\n{method.upper()}\n{target}\n".encode() + body
    mac = hmac.new(secret.encode(), signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(mac, v2)
```

### Agent skill and api_version

The relay is just a relay: it does not serve, version or announce the agent skill.

- **One skill, in the repo:** `skills/molty/` — a short `SKILL.md` core plus `references/`
  (API, events, talking fast, etiquette, voice, voice box, updates, activity, self-hosting,
  per-harness setups) and shell helpers in `scripts/`. `tools/scripts/check-skill.mjs` (run by
  `make hygiene`) checks it against the code: every command, mood and MCP tool documented, the
  links, no hard-coded relay host, the manifests.
- **Distributed only through the git plugin marketplaces.** The repo root is the plugin
  (`.claude-plugin/{marketplace,plugin}.json`, `.codex-plugin/plugin.json`,
  `.agents/plugins/marketplace.json`; Codex only finds skills under `<plugin root>/skills/`):
  `claude plugin marketplace add apresmoi/molty.uno && claude plugin install molty@molty`,
  `codex plugin marketplace add apresmoi/molty.uno && codex plugin add molty@molty`. The
  manifests carry no `version`, so an update follows the repo's commits. Agents without a plugin
  system read it on GitHub.
- **`api_version`** (`API_VERSION` in `services/relay/src/core/version.ts`, an integer, now **1**): the
  agent API contract, bumped only when an agent built for the previous one would break or miss
  something it must handle. Stated in the pair result, `status` → `relay.api_version`,
  `GET /v1/health`, `molty_updates` and the MCP `serverInfo.title` / `instructions`. The skill
  names the `api_version` it targets; an agent that sees a higher one asks its human to update the
  plugin. What a given Molty can do stays `relay.caps`.
- **Backward compatibility:** `GET /skill.md` (and `/skill`) answers `301` to
  `https://raw.githubusercontent.com/apresmoi/molty.uno/main/skills/molty/SKILL.md`
  (deprecated). The former skill-version machinery is gone: no `skill_update` ride-along, no
  `skill.updated` event, `molty_updates` has no `skill` block. Tokens and rooms from before keep
  their stale `skill_seen` / `skillev` / `origin` values; nothing reads them.

### Firmware updates

"Check Molty for updates" is one agent call. Everything below is relay code
(`services/relay/src/core/{releases,updates,version}.ts`) except the device wire, which the
firmware implements.

```
GitHub Releases (RELEASES_REPO) ─▶ releases singleton DO (1 h cache, stale on error)
                                        │
           molty_updates / molty_status / ride-along notice / molty_update
                                        │
           molty_update ─▶ cmd update ─▶ device: "update?" on screen ─▶ download + sha256
                                        ─▶ flash ─▶ reboot ─▶ hello fw=new ─▶ job done
```

**Latest release.** `https://api.github.com/repos/<RELEASES_REPO>/releases/latest` (wrangler
var, default `apresmoi/molty.uno`; optional secret `GITHUB_TOKEN` for the higher rate limit).
One Durable Object instance (`releases`) caches it for everyone: GitHub is asked about once an
hour, at most once a minute after a failure, and the last good answer is served stale when
GitHub fails. One 2 s deadline covers a refresh; agent calls never wait longer. No release yet
is a normal answer (`latest:null`). Prereleases and drafts are ignored unless
`RELEASES_PRERELEASE=true`. Per board, the OTA image is the asset `molty-X.Y.Z-<board>-ota.bin`
whose URL is exactly `https://github.com/<repo>/releases/download/vX.Y.Z/<name>`; its sha256
comes from the release's `SHA256SUMS` (GitHub's asset digest as fallback; if they disagree,
none). Only these URLs ever reach the device — `molty_update` takes no arguments.

**Feature → minimum firmware.** `FEATURES` in `services/relay/src/core/version.ts` is the one place:
`ask` → `molty_ask`, `update` → `molty_update`, both `NEXT_FW` = **0.2.0** (the next release).

**`molty_updates`** (REST `GET /v1/devices/<id>/updates`), ride-alongs included:

```
{"api_version": 1,
 "firmware":{"current":"0.1.0", "board":"…", "online":true, "latest":"0.2.0"|null,
             "status":"current"|"update_available"|"no_build_for_board"|"no_release"|"unknown",
             "update_available":true, "published_at":"…", "notes_url":"…",
             "needed_for":[{"feature":"molty_ask", "what":"…", "needs":"0.2.0", "released":true}],
             "can_self_update":false, "release_check":"fresh"|"stale"|"unavailable"},
 "actions": ["Tell your human Molty firmware 0.2.0 is out …"]}
```

It marks the reported release as seen for the calling token. `status` is
`unknown` when the device reports a non-release version (`dev`, a local build) or the release
list was never reachable. Offline devices are answered from their last hello (`online:false`).
`molty_status` carries the same block as `relay.firmware`.

**Passive notice.** Once per token per newer release (`fw_seen` on the token, written
atomically on the current token record, never resurrecting a revoked one), the next successful authenticated response carries `firmware_update:
{current, latest, board, notes_url, can_self_update, how}` (MCP: plus the line "Molty firmware
X is out (Molty runs Y). …"). It never waits on GitHub (cached answer only).

**`molty_update`** (REST `POST /v1/devices/<id>/update {}`): needs `update` in the device's
caps (else `409 unsupported` with `{current, latest, how}` pointing at the console). Already
current or nothing released: `{status:"up_to_date"}`, no job. Otherwise a job (`kind:"update"`,
blocks ≤ 24 s, then `molty_wait`), stored in the room (`upd`), so it survives the relay host's
eviction and the device's reboot:

| phase | set by |
|---|---|
| `confirm` | relay sent `cmd update`; the device shows the question |
| `accepted`, `downloading`, `flashing`, `rebooting` | the device's `update` events |

Ends: `done {outcome:"updated", from, to}` when the device's next hello reports `fw == to`;
`done {outcome:"declined", reason?}`; failed `update_failed` (device reported `failed`; `detail`
names why), `rolled_back` (a hello on another version after `rebooting`), `update_timeout`
(no answer within `timeout_ms` + 5 s, or not back on the new version 5 min after the accept).
A hello on the old version before `rebooting` (a Wi-Fi blip mid-download) is not a failure.
A lost `cmd update` ack (`device_timeout`) does not fail the job: delivery is unknown, the
question may be on screen, so `upd` stays tracked through the confirmation deadline and a later
`accepted` / progress event, a decline, or a hello on the new version still settles it (none:
`update_timeout`). A refusal (`res ok:false`) or an offline device fails it at once.
A second `molty_update` while one runs returns that job.

**Device wire (firmware contract).**

- Hello lists `update` in `caps` once the firmware implements this.
- Relay → device: `{"t":"cmd","id":"c9","name":"update","args":{"job":"<job>","version":"0.2.0",
  "url":"https://github.com/<repo>/releases/download/v0.2.0/molty-0.2.0-<board>-ota.bin",
  "sha256":"<64 hex>","size":1234567,"timeout_ms":60000}}`.
  The device acks (`res ok`) once the question is on screen: reuse the ask screen with two
  options, the version (green: tap to install it) and "later" (white). The ask screen has no
  header, so the green option's label *is* the version: `v0.2.0`, or the bare version when the
  `v` would push it past the 8-character label limit (`10.10.10`). Refuse with `res {ok:false, error}`:
  `busy` (an update already running), `bad_url` (not `https://github.com/<repo>/releases/download/…`
  for the repo baked into the firmware), `wrong_board`, `version_too_long` (the version does not
  fit an 8-character label, so the question could not show it; update from the console instead).
- Device → relay events `{"t":"evt","name":"update","data":{"job":"<job>","state":…}}`:
  `declined` (+ `reason:"timeout"|"cancelled"`: no tap within `timeout_ms`, or another accepted
  command replaced the question — the same tap, deadline and cancellation rules as `ask`), `accepted`, `downloading` (optional `progress` 0..1, at most 1/s),
  `flashing`, `rebooting` (sent right before `esp_restart`), `failed` (+ `error`, a short ASCII
  reason, e.g. `sha256_mismatch`, `size_mismatch`, `http_404`, `tls`, `wrong_board`, `write`).
- Download over HTTPS with certificate verification (GitHub redirects to its asset CDN: follow
  it), into the spare OTA slot (`esp_ota_*`, as `POST /api/ota`), checking the board tag like
  `/api/ota`, then `size` and the sha256 of the whole image; on any mismatch abort and send
  `failed`. Only then set the boot partition, send `rebooting`, restart.
- After the restart, the new app reconnects and says hello with its new `fw`; it should mark
  itself valid (`esp_ota_mark_app_valid_cancel_rollback`) only after the link's `welcome`, so an
  image that cannot reach the relay rolls back by itself and comes back on the old version.

**Console.** The status page asks the device's relay `GET /v1/releases/latest?board=<board>`
(public, no device data) and shows "update available: X.Y.Z — what's new". With the device's
`GET /api/update` present (firmware with self-update) its Update button posts
`POST /api/update {version, url, sha256, size}` from that answer; otherwise it links the OTA
image and uploads a chosen file to `POST /api/ota`.

### Example setups by agent kind

These are examples, not rules; the skill deliberately lets each agent choose (its
`references/harnesses/` spell these out per harness).

- **Shell-capable, long-running (Claude Code, Codex CLI, local OpenClaw).** Run the CLI as
  a background process and treat each output line as a wake-up.
  - Claude Code: start `molty events` with the Bash tool's `run_in_background`, then watch
    it with the Monitor tool (or read its output file between turns); each JSON line is one
    event. Example: `molty events --exec 'cat >> ~/.molty-events.jsonl'`.
  - Codex CLI / local OpenClaw: launch `molty events --exec '<your wake hook>'` as a
    long-lived child (or a `systemd --user` / `launchd` service) whose `--exec` command
    posts to the agent's local wake endpoint or appends to the file it watches.
- **Server-hosted (bots on xAI/OpenAI/Anthropic APIs, cloud OpenClaw).** Register a
  webhook pointing at the bot's own HTTPS endpoint (default body, verify the signature), or
  directly at the platform's message/run API with a template.
- **Chat apps (ChatGPT, claude.ai, Claude Cowork, grok.com).** No endpoint, not running
  between turns: rely on ride-along, and call `molty_events` at the start of a turn when
  the human is talking about Molty. Do not claim to react live.

## Voice box

The owner's own GPU machine can do Molty's speech (STT + TTS) instead of the relay's
cloud provider. Reference implementation: `services/molty-voice/` (`molty-voice`, bridging Kyutai's
moshi-server). The device does not change: it talks to the relay as always. The box is one
more relay client that **dials out** to the relay over WSS (no inbound ports, no tunnel).

```
Molty ──WSS /v1/device──▶ relay (DO per device) ◀──WSS /v1/voice── voice box ──▶ local STT/TTS
                            │  record(): mic chunks forwarded to the box AS THEY ARRIVE
                            │  speak():  box PCM streamed to Molty as it arrives
                            └─ cloud provider (env) when the box is absent (mode auto)
```

### Pairing and tokens

- Same flow as an agent: `POST /v1/pair {device_id, link_code, agent_name, role:"voice"}`,
  code on the device, the human taps. The device is sent
  `agent_name: "voice box · <name>"` (unchanged when the name already starts with
  "voice box"). The firmware shows only the code; the console names the request. No
  firmware change.
- The approved reply carries `role:"voice"`. The token (same `<device_id>.<43 chars>`
  shape, the field is still `agent_token`) is stored with `role:"voice"`.
- **Role isolation:**
  - A voice token is refused on every agent call: REST, MCP, jobs, inbox, webhooks,
    updates. The error is `403 forbidden` ("this is a voice box token…").
  - An agent token is refused on the voice socket (`403`).
  - An unknown or revoked token is `401`.
- **Revoke:**
  - `DELETE /v1/token` works for a voice token and closes its socket (4401).
  - The console can unpair the box (below).
  - Forgetting the device drops the box and its settings.
- **One box per device:** approving a new voice pairing deletes the older voice tokens
  and closes their sockets.

### Voice socket

`GET /v1/voice?device_id=<id>` (WebSocket upgrade), `Authorization: Bearer <voice token>`.
The worker routes it into the device's Durable Object.

- **Auth:** the token is checked before the upgrade is accepted. A refused box gets the
  HTTP status (401/403), never an open socket.
- **Hibernation:** the socket is hibernatable like the device's. Its role lives in its own
  attachment (`SocketMeta.stage = "voice"`), never in instance fields. No device code path
  ever sees it.
- **One active box per device:** a new connection replaces the old one, which closes with
  4409 and fails its in-flight requests at once.
- **Keepalive:** `{"t":"ping"}` → `{"t":"pong"}`, answered by the runtime without waking
  the object.

Wire: JSON text frames plus binary audio frames in the device's framing
(`<JSON header>\n<payload>`, header ≤ 512 B, payload ≤ 16 KB, PCM16 mono @16 kHz), with
the request id in `s`.

| Direction | Message |
|---|---|
| box → relay | `{"t":"voice.hello","name","version","voices":[…],"stt":bool,"tts":bool,"reflex"?:bool}`: first frame; the box is used only after it. `reflex: true`: it runs the [reflex](#reflex) classifier (stt.reflex) |
| relay → box | `{"t":"voice.welcome","device_id","mode","voice"}` |
| relay → box | `{"t":"tts","id","text","voice"?}`: one sentence-sized segment (the relay keeps one segment of lookahead) |
| box → relay | binary frames `s=id` (PCM16 @16 kHz, as synthesised), then `{"t":"tts.end","id"}` or `{"t":"tts.end","id","error"}` |
| box → relay | `{"t":"tts.word","id","i","text","start_s"}` (optional, in order, before the tts.end): word `i` of the text (whitespace-split) is spoken from `start_s` s into this tts's audio as sent — moshi-server's `Text {text, start_s, stop_s}` less one 80 ms step (its counter runs one step ahead: measured +91 ms median against forced alignment) and less the quiet lead the box trimmed from the stream's first frame (≤ 70 ms). The relay turns it into the device's word cues; malformed ones are ignored |
| relay → box | `{"t":"tts.cancel","id"}`: nobody will play it (device gone, turn failed, segment timeout) |
| relay → box | `{"t":"stt.start","id","rate":16000,"no_speech_ms"?,"reflex"?:true}` at listen start (`reflex` only to a box that offered it, when this listen's [reflex](#reflex) uses the local engine) (`no_speech_ms` 1000..10000 only when the device VAD is off for this listen: the box then calls no_speech), binary frames `s=id` as Molty records, `{"t":"stt.end","id"}` at the device's end frame |
| relay → box | `{"t":"stt.cancel","id"}`: no speech, or the listen failed |
| box → relay | `{"t":"stt.partial","id","text"}` (optional, ignored by the relay), `{"t":"stt.final","id","text","ms"?}` or `{"t":"stt.final","id","error"}` |
| box → relay | `{"t":"stt.turn_end","id","reason":"no_speech"}` (only when `stt.start` carried `no_speech_ms`; at most once, never after a word or a turn end): nobody spoke for `no_speech_ms` of captured audio — no word, no voice activity (the model's `prs[2]` below 0.3 for 3 steps restarts the clock; a loud frame in the last ~0.5 s postpones the verdict) — and nobody is speaking right then. The relay ends the listen as the device's own no_speech: `listen_stop {job, reason:"no_speech"}` (no chirp, no thinking), `stt.cancel`, `reason:"no_speech"`, `heard:""` |
| box → relay | `{"t":"stt.turn_end","id"}` (optional, at most once per listen): the human finished. The relay ends the listen there (`cmd listen_stop` to firmware with the cap, `stt.end` to the box at once); see `listen_stop` above |
| box → relay | `{"t":"stt.hint","id","k":"pause"\|"question"}` (optional, while the human talks; ≥ 1.5 s apart): `pause` = a mid-turn pause began (the pause estimate crossed the threshold after a word, before any turn end), `question` = a word ending in `?` arrived. Forwarded to firmware with the cap `hints` as `hint` while that listen is open; dropped otherwise |
| box → relay | `{"t":"stt.reflex","id","n","pick","conf","p":{…},"cat","cat_conf","ms","chars","tokens","model"}` (only after `stt.start` with `reflex: true`): the box's classifier on [reflex](#reflex) chunk `n` (the text so far had `n` words), right after that word's `stt.partial`. The relay validates it, gates `conf` and uses it for that chunk; late or unknown chunks are only noted |
| box → relay | `{"t":"stt.trace","id","trace":{…}}` (optional): the box's side of the [turn trace](#turn-trace), sent right before `stt.turn_end` (either kind) and again right before `stt.final` (the last one wins, ≤ 8 KB, known keys only). An older relay ignores both |

### Selection: `voice_mode`

A per-device owner setting, read for every say and every listen:

| Mode | Behaviour |
|---|---|
| `auto` (default) | The box when it is connected, greeted, and offers that direction (`stt` / `tts` in its hello); otherwise the env provider. |
| `box` | The box only. Without it, the job fails `voice_box_offline` (REST 503) before anything reaches the device. |
| `cloud` | The env provider always. |

How the paths work:

- **Streaming STT:** with the box, `record()` opens `sttStream()` before `cmd listen` and
  pushes every device chunk as it arrives. At the end frame it waits at most 5 s
  (`boxSttFinalMs`) for `stt.final`.
- **Box drops mid-listen, `auto`:** the relay falls back to the env provider's batch STT
  on the audio it buffered anyway. This also covers no final in time and a box error.
  `timings.voice_fallback` says why (`voice_box_offline`, `stt_timeout`,
  `voice_box_error`).
- **Box drops mid-listen, `box`:** the job fails.
- **Box drops before its TTS audio:** the segment fails at once (`voice_box_offline`),
  with no hang; the say the device was already told about (`cmd say` leaves with the box's
  tts request) gets a header-only end frame, so its speaker is free at once. If it drops mid-stream, the
  device's stream is closed as for any TTS failure.
- **Semantic end of turn:** `molty-voice` sends `stt.turn_end` by Kyutai Unmute's pause rule:
  an EMA of the STT's per-step pause estimate `prs[2]` (half-life 0.01 s, starting at 1.0, the
  first 12 steps ignored, `--turn-end-skip`) above 0.6 (`--turn-end`), once, and only after at least one word —
  silence alone never ends a turn (the device's `no_speech` does). The listen then ends with
  `reason:"turn_end"` instead of waiting for the device's silence timer or its window.
  **Mid-sentence hold:** the pause ends the turn at once only when the transcript's latest word
  ends a sentence (Kyutai punctuates its words: a final `.` `?` `!`, not an ellipsis, not a bare
  "um."). Otherwise — no mark, a comma, "…2 meters from" — the pause must stay above the
  threshold for `--turn-end-hold` seconds of model steps (default 1.2; 0 = Unmute's rule). Words
  lag the voice by ~0.5–1.6 s, so each step judges the latest word received: a sentence's
  closing word that lands during the hold ends the turn then, and any word landing during the
  hold restarts it (as does the voice coming back). A thinking pause inside a sentence
  (~0.6 s, live 2026-10-30) no longer cuts the human off; a finished sentence ends as before.
- **Voice choice:** the agent's `voice` passes through to the box. With none, the
  owner's default box voice is used; with neither, the box picks its own.
- **Timings:** every say / listen timing payload carries `voice` (`"box"` or the env
  provider's name). For talk / ask that is `timings.say.voice` and `timings.listen.voice`.
- **Status:** `molty_status`'s `relay.voice` names who would speak now (`box`, the env
  provider, or `voice_box_offline`).

Providers without `sttStream` (Workers AI, OpenAI, none) keep the batch path unchanged.

### Owner API (console)

`GET|POST|DELETE /v1/devices/<id>/voice` with the header
`X-Molty-Link-Code: <the device's current link code>`. The route answers CORS, because
the console is served by the device.

- **Auth model:** being on Molty's network makes you the owner, the same model as every
  local device setting. The console reads the code from `GET /api/link`; it rotates every
  15 min and after each pairing.
- **GET** returns `{mode, voice, cloud, serving:{tts, stt}, reflex:{mode, compare, engines:{local,
  jev, openai, keywords}, engine, fallback?, timeout_ms, liveliness}, box:{paired, name, paired_at,
  connected, connected_since, reported_name, version, voices, stt, tts, last:{stt_ms,
  tts_first_audio_ms, …}}}` (`reflex.engine`: what the next listen fires with, null when off).
- **POST** `{mode?, voice?, reflex?, reflex_compare?, liveliness?}` changes the settings (`voice:
  null` = the box's default; `reflex` one of `off auto local jev openai keywords`, `liveliness` one
  of `calm normal lively`, see [Reflex](#reflex)).
- **DELETE** unpairs the box.
- **Errors:** `401` for a wrong or expired code, `400 invalid_args`.

The console's agent page has a **Voice** card with:

- the mode;
- the box status and last latencies;
- the default box voice;
- unpair;
- the `molty-voice pair` command, filled in.

## Activity log

One timeline of everything that happens on a Molty, and which agent did it — so a failed turn
can be read in one place instead of lining up the agent's memory, the device log and a live
`wrangler tail`. Code: `services/relay/src/core/activity.ts` (relay), `device/firmware/main/diag/log_upload.c`
(device), `device/console/src/activity/` (console's **activity** page).

### What is recorded

| kind | when | fields |
|---|---|---|
| `call` | every authenticated agent call (successful `wait` / `events` polls are skipped: they would wash the log out) | `agent`, `op` (`talk`, `say`, `mood`, `status`, …), `args` (summary: secrets stripped), `ok` / `error` / `message`, `ms`, `job` when it made or names one; `status` adds `data.rssi` |
| `job` | a job ends (`ts` = its start) | `op` (job kind), `agent`, `ok` / `error`, `ms`, `data: {status, timings, voice:{tts?, stt?, fallback?}, reason?, heard?, said?, answer?, index?, outcome?, phase?, trace?, audio?}` — `trace`: a listen's (listen / talk / adopted shake) [turn trace](#turn-trace), failed ones too; `audio: true`: its audio is kept ([Keep audio](#keep-audio-for-debugging)) |
| `trace` | later facts about a turn (`job` = the turn's listen job): `webhook` (each delivery attempt of its `utterance`), `reply` (a say / talk answering it) | `ev`, `agent`, `data` ([Turn trace](#turn-trace)) |
| `device` | `connect` (`fw`, `board`), `disconnect` (`code`: the close code), `refused` (wrong device key), `shake` / `tap` / `button`, `utterance` (shake to talk: `job` = its `turn_id`, `data: {text, reason, trigger, words, partials, drafts, draft?}`; the text is a transcript), `draft.used` / `draft.dropped` (`job` = the turn, `agent`: the drafter — visible to it; `data: {opener?, reason?, based_on, new_words?, say_job?}`), `draft.misfire` (a shake over an opener) | `ev`, `data` |
| `device_log` | the device's own log lines (below) | `job` when tagged, `data: {text, level: E\|W\|I\|D\|V\|EVT, boot, seq, prev?, approx?}` |
| `pair` | `approved` / `rejected` / `timeout` / `revoked` | `ev`, `agent` |
| `voice_box` | `connect` / `disconnect` / `unpaired` | `ev`, `data` |
| `settings` | owner changes: `voice` (mode, voice), `activity` (transcripts, keep_audio); `calibration` (the relay's own: `threshold {from, to}`, `partials {source, every_words, every_ms, lead_ms}`, `reset`) | `ev`, `data` |

Every entry is `{id:"a<seq>", ts, kind, …}`. A refused answer to someone else's turn is a `call`
with `error: "turn_claimed"`; the adopted shake listen is a `job` with no agent (owner only). Failed `talk` / `ask` / `update` calls also return
their job id as `job` next to `error`, so an agent can look the turn up.

**Secrets** never reach storage: keys named like secret / token / key / auth / password /
cookie / signature / credential / link_code / headers / code, and bearer- or token-shaped
values anywhere (also inside free text: a say, a transcript, a device line), become `"[secret]"` —
one sanitizer at the log's single write path, for every entry kind and field; webhook
registrations keep only the redacted URL (origin), the method, the number of headers and
whether a body template is set.

`notes` calls keep the op and the key, never the value.

**Transcripts** (`heard`, `said`, say / show text and draft openers in call args, an `utterance`'s text, a `draft.used` opener) are kept by default (≤ 500
chars each). The owner's setting **log transcripts: off** removes them *before the write*
(the entry keeps its metadata and gets `redacted: true`); turning it on again affects new
entries only.

### Limits (Durable Object storage)

Entries go into chunks (`al:c:<n>`, ≤ 64 entries / ≤ 16 KB each) behind a head pointer
(`al:h`): an append reads the pointer and the head chunk and writes the head chunk back — one
row written, which is what a SQLite-backed Durable Object bills, whatever the size. Kept:
**the last 24 h, and at most 48 chunks (≤ 768 KB, ≤ 3072 entries)**, whichever is smaller;
older chunks are deleted as the head moves on, and nothing older than 24 h is ever returned.
A busy device (~500 turns a day, ~10 entries each) fits; storage stays under 1 MB per
device. Device lines are capped at 64 per frame and 240 per minute; device events at 60 per
minute. Forgetting the device deletes the log.

### Device log lines

The firmware tags every log line written while a relay job runs (say, listen, ask, update)
with the job id's random part (`[j_<tag>]` in `/api/log` text, `"job"` in its JSON). With the
`log_upload` cap and a welcome that carries `log`, it uploads:

`{"t":"log","boot":<n>,"up":<uptime ms>,"lines":[[seq, ms, "<tag>", "<text>"], …]}` —
at most `max_lines` lines (oldest first, text ≤ 150 chars, frame ≤ 12 KB), only lines worth
it: job-tagged lines, `E` / `W` lines and `EVT` lines (not the routine 10 s `EVT TL` timeline,
but its `TL!` trouble form). Sent after each welcome (the previous boot's lines once, as
`"prev":true` with that boot's `"sync":[uptime ms, relay ms]` from its last welcome, then the
current backlog, newest two frames at most) and after each job ends; at most one frame per 2 s.

The relay maps the tag to `<device_id>.j_<tag>`, converts uptime to wall time (`receive time −
(up − ms)`; previous boot: `sync[1] + (ms − sync[0])`, or its receive time with `approx:true`
when that boot never had a welcome) and skips lines it already has (by `boot` + `seq`). An
older relay ignores the frame.

The device keeps a persistent copy for power loss: `/spiffs/diag.log`, a header
`#molty-log 2 boot=<n> sync_up=<ms> sync_wall=<ms>` then `<seq> <ms> <tag|-> <text>` lines
(newest 12 KB). Written on an error line or important event, and on the 30-minute tick only
when an uploadable line arrived since the last write; never in the first 90 s after boot and
at least 5 minutes apart (≤ 288 small writes a day even with errors all day; typically a
few). Soft resets (panic, watchdog, OTA restart) are covered by the no-init RAM ring.

### Reading it

- **Owner** (console): `GET /v1/devices/<id>/activity?since=a42|<unix ms>&limit=1..500&agent=<name>&kind=call,job&job=<job id>&errors=1`
  with `X-Molty-Link-Code` (same auth and CORS as the [voice owner API](#owner-api-console)) →
  `{entries, next, more, transcripts, keep_audio, audio:{turns, max_s, max_age_h}, limits:{max_age_h, max_entries}}`, entries oldest first.
  `since=a<id>`: entries after it, `limit` at most (`more` when cut; resume from `next`); no
  `since`: the newest `limit` (default 200). `POST {transcripts?: bool, keep_audio?: bool}` (one
  or both) sets the settings.
- **Agents**: `GET /v1/activity?since&limit&kind&job&errors` (bearer) or MCP `molty_activity` →
  `{entries, next, more}`: **only that agent's own** calls, jobs and pairing, the device lines of
  its own jobs, and the device's connects / disconnects within its jobs' spans (5 s before to
  30 s after). Never another agent's entries or transcripts; `agent=` is ignored. Voice box
  tokens are refused (`403`).
  "Its own jobs" means the relay's job record says that agent's token started them (written by
  the relay when the job is created); naming a job id in a call never makes it yours. An
  `audio_busy` refusal does not name the running job.

### Keep audio for debugging

An owner setting, **off by default** (console Activity › "keep audio", `POST …/activity
{keep_audio: true}`). While on **and** log transcripts are on, the relay keeps each listen's
audio as it received it (PCM16 @16 kHz, seq order, the first 30 s): the newest **5** listens,
each deleted **24 h** after capture (on write, on read and on the room's alarm, which is
scheduled for it beside webhook deliveries). Storage: `aud:` keys, 64 KB pieces (≤ ~4.8 MB per
device). Transcripts off ⇒ none is kept and what was kept is deleted; keep audio off deletes it
too; forgetting the device deletes it. The job entry says `data.audio: true`.

Download: `GET /v1/devices/<id>/activity/audio/<job id>` with `X-Molty-Link-Code` → `200
audio/wav` (CORS like the activity route), `401` wrong code, `404 not_found` when never kept or
expired. **Owner only**: the route reads the link code alone — no agent token opens it, and
there is no agent route to audio.

## Turn trace

Everything about one listen in one place, so a bad turn (garbage transcript, lost audio, a slow
answer) can be read without a device log, a box log and a `wrangler tail`. Code:
`services/relay/src/core/trace.ts` (relay), the frame fields above (device), `stt.trace` (box).

Stored with the job: the listen's activity `job` entry carries `data.trace` (≤ **4096 B** of
UTF-8 JSON; when bigger, trimmed in this order until it fits — the frame list to its first/last 8,
the box's pause series halved then dropped, its words to the last 16 then dropped, the device
levels halved by max (`lv_ms` per byte), the box's activity spans; `trimmed: true`). Never in the
agent-facing job result. Older firmware or bridge: those parts are simply absent. A listen the
relay ended (the box's turn end / no_speech) usually ends before the device's own end frame: its
later frames still count for the trace — header diagnostics (`tr`, levels, `late`) only, their
audio goes nowhere — from the moment the relay stopped taking its audio until that end frame,
3 s, or the device's disconnect; the job's entry is written then, once (the agent's result never
waits for it). Forgetting the device voids every such delayed write (entry, kept audio). A listen whose STT failed (`stt_timeout`, a provider error)
keeps its trace on the failed job's entry.

```json
{"v":1,"trigger":"shake","t0":1793410484862,
 "dev":{"shake":{"at":-140,"peak_g":8.2,"rev":4,"ms":420},"set":340,"setc":0,"wall":1400,"cap":1060,
        "gain":6,"pk":998,"lv":"a0b0c0a1a1a1a2a2a290","lv0":340,"clip":[[3,3]],"clip_n":3,
        "frames":[[0,340,0,0,20],[2,940,1,0,30],[1,640,1,2,1500],[3,1240,2,0,null]],
        "sent":4,"fail":2,"resent":1,"late":1,"dup":1,"rssi":[-69,-79],"end":"turn_end"},
 "box":{"v":1,"step_ms":80,"skip":12,"thr":0.6,"hold_s":1.2,"audio_s":1.2,"act":[[0.3,1]],
        "pause":"ffeeddccbb","pause_every":2,"words":[["hi",0.32,0.5],["Molty,",0.5,null],["today?",0.9,1.1]],
        "end":{"at":1.12,"rule":"punct","word":"today?","held_s":0,"ema":0.71},"final_ms":7},
 "relay":{"voice":"box","cmd":2,"first_frame":1,"turn_end":2,"end":2,"stt":4,"utterance":6,"hints":[["question",1]]}}
```

- `t0`: relay ms when the listen began; every other relay time (`dev.frames` arrivals,
  `dev.shake.at`, `relay.*`, hints) is ms from it.
- `dev`: the shake (its event's arrival, peak g, reversals, its detection ms), the device's `tr`
  summary, `lv` the levels over the whole listen in capture order (one byte per 100 ms, as the
  frames' `lv`; a hole between frames reads `00`; `lv0` = the `ct` of its first byte), `clip`
  `[[chunk index, saturated samples]…]`, `frames` `[[seq, ct, arrival, rt, wq]…]` in arrival order,
  `sent` / `fail` / `resent`, `lost` `[[from seq, to seq]…]` (gaps the relay gave up),
  `lost_ms` (the device's dropped audio), `late` / `dup`, `rssi` `[start, end]`, the end `reason`
  and `speech_ms`.
- `box`: the voice box's `stt.trace` — `act` speech-activity spans and `words`
  `[[text, start, stop|null]…]` in audio seconds, `pause` the pause estimate (one byte = round(EMA·255)
  per `pause_every` 80 ms steps), `end` the end-of-turn decision (`at` audio s, `rule`: `punct` the
  last word ended a sentence / `hold` a mid-sentence pause that lasted the hold / `unmute` hold 0,
  `word`, `held_s`, `ema`), `ns` the no-speech decision (`at`, `quiet_s`, `ema`, `why`),
  `final_ms` the transcript's tail after the end.
- `relay`: who transcribed (`voice`, `fallback`), `cmd` (listen acknowledged), `first_frame`,
  `turn_end` (the box's), `end` (the end frame or turn end), `stt` (ms of transcription after
  the end), `utterance` (when it went to the agents), `hints` `[[k, ms]…]` forwarded to Molty,
  `audio_kept`.
- Log transcripts off: the box's `words` and the end's `word` are emptied before the write.

Later facts are `trace` entries on the turn (`job` = its listen job id), attributed to the agent
(an agent sees only its own, an owner all):
- `ev:"webhook"` — each delivery attempt of the turn's `utterance` to an agent's webhook:
  `ok`, `data:{status (HTTP, null when none came), ms (the request), attempt, after_ms (from the
  utterance to the delivery's end), error?}`.
- `ev:"reply"` — a say / talk answering the turn (claimed, or `in_reply_to` it) or an ask with
  `in_reply_to` it, once its say has played: `data:{op, job (the reply's job), reply_ms, first_audio_ms, client_timing?}`.

**Listener reactions** (firmware cap `hints`): while the human speaks, Molty reacts by itself —
visual only, subtle, never over a question / pairing / update, never with idle life off: a nod
at a natural pause (the box's `pause` hint, else the device's own level-based pause), a glance at
a question (`question` hint), a small look-up when the voice starts after a quiet stretch. None
in the first second of a listen, ≥ 2.5 s apart (5 s with idle life "calm").

## Default relay

Each component has exactly one default relay URL, all set to the same value
(`molty-relay.alicenet.workers.dev`, the project's hosted relay). Change it in these
places to point a build at your own relay (see `services/relay/README.md` to deploy one):

| Component | Where | Used when |
|---|---|---|
| firmware | `CONFIG_MOLTY_DEFAULT_RELAY` in `device/firmware/main/Kconfig.projbuild` (`wss://…`) | no relay URL saved in NVS (`POST /api/link {relay_url}` overrides) |
| console | `DEFAULT_RELAY` in `device/console/src/agents/agents.ts` (`https://…`) | the device has not reported a `relay_url` yet; the setup message names the relay only when it differs |
| skill | `MOLTY_DEFAULT_RELAY` in `skills/molty/scripts/_config.sh` (and `watch.py`, `SKILL.md`) | `MOLTY_RELAY` is unset (env or `~/.config/molty/env`) |
| CLI | `DefaultRelay` in `apps/cli/internal/molty/link.go` (`https://…`) | `molty pair` without `--relay` / `MOLTY_RELAY` |

The website's waitlist form posts to the same hosted relay (`WAITLIST_URL` in
`apps/website/src/config/site.mjs`, `POST /waitlist`, services/relay/README.md "Waitlist"); it is not part
of the agent link.
