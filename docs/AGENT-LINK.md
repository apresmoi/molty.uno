# Agent link — v0 spec

**Status:** v0. Goal: any agent, anywhere, drives Molty with **no laptop in the loop**.
Built to be swapped module by module. Background and design rationale:
[ARCHITECTURE.md](ARCHITECTURE.md).

```
Molty (home Wi-Fi) ──outbound WSS──▶ molty-relay (Cloudflare Worker + Durable Object)
                                       ├─ /mcp   remote MCP (HTTPS)   ◀── any MCP client (Claude, Grok, …)
                                       ├─ /v1/*  REST                 ◀── molty CLI --relay, scripts
                                       ├─ voice  TTS/STT provider     (Workers AI first; swappable)
                                       └─ (later) OpenClaw node adapter
```

## Modules and seams (each swappable)

| Module | Where | Swappable seam |
|---|---|---|
| Relay core (rooms, auth, pairing, routing, jobs) | `relay/src/core/` | pure TS, no Cloudflare imports |
| Relay host | `relay/src/worker.ts` (+ DO) | another host (Node server) wraps the same core |
| Agent surfaces | `src/surfaces/mcp.ts`, `src/surfaces/rest.ts` | add OpenClaw node adapter beside them |
| Voice provider | `src/voice/*.ts` → `interface VoiceProvider { tts(text, opts) → PCM16@16k; stt(PCM16@16k) → text }` | workers-ai · openai · none |
| Device link client | `firmware/main/link/` | transport only; commands come from the dispatcher |
| Device command dispatcher | `main/link/link_cmd.c` | ONE registry used by both the WSS link and (later) local HTTP |
| Pairing UI | static: the 4-digit code alone, held as one centred token in the fluid text target (no ORP accent), until accept/reject/timeout (`link_ui_show_pair`); agent name is shown by the console via `GET /api/link` | a dedicated `pair` creature state is the planned upgrade |

## Identities and secrets

- `device_id` = `molty-` + 10 random chars `[a-z2-9]` (e.g. `molty-k7m2w9c4ya`). Public,
  generated together with the key on first boot and persisted in NVS. It is unrelated to
  the MAC; unpredictable IDs prevent guessing a new device's TOFU room before it connects.
- `device_key` = 32 random bytes, generated with the ID on first boot, kept in NVS. The device sends
  it on every connect. The relay stores `sha256(device_key)` on first claim of a
  `device_id` (trust on first use); later connects must match. Console "forget link" sends
  `{"t":"forget"}` on the authenticated socket, waits up to 3 s for close 4410, then wipes
  the NVS identity and relay URL. The next identity has a fresh ID **and** key. If offline
  or the relay does not acknowledge, local erasure still proceeds; remote revocation is
  confirmed only by 4410. Older key-only installations migrate to a new random ID/key.
- `link_code` = 8 chars `[A-Z2-9]`, generated by the device, shown in the console's
  "Connect an agent" instructions, rotates every 15 min and after each successful pairing.
  Stops strangers from spamming pair requests: a pair request must carry a valid link_code.
- `agent_token` = 32 random bytes (base64url), issued by the relay after on-device approval.
  Relay stores only its hash, scoped to one `device_id`, with the agent's name. Revocable.

## Pairing flow

1. Console (USB or `molty.local`) → Wi-Fi set → "Connect an agent" → the user pastes ONE
   message into any agent:
   ```
   Hi! Please connect yourself to my Molty.

   Instructions: <relay https origin>/skill.md
   Device: molty-xxxxxxxxxx
   Code: K7M2W9C4

   I'll tap Molty to accept you.
   ```
   `GET <relay>/skill.md` (also `/skill`, `text/markdown`) is the agent-facing guide: what
   Molty is, pairing over plain HTTPS, the REST command table, the optional MCP route,
   etiquette. All URLs in it are built from the request origin
   (`relay/src/surfaces/skill.ts`).
2. The agent calls `POST /v1/pair {device_id, link_code, agent_name}` (or the `molty_pair` MCP
   tool, which is the only tool usable without a token). The request long-polls ≤ 120 s.
3. Relay → device: `pair.request {req, agent_name, code}` where `code` is 4 digits.
4. Device shows the 4-digit `code` statically (one held token in the fluid) until decided
   (touch tap or BOOT button = accept; PWR = reject; 110 s = `timeout`, so the device
   decides just before the relay's 120 s window closes). The console polls `GET /api/link`
   (~1 Hz) and advances on `pair` / `last_pair`.
5. Device → relay: `pair.result {req, ok}`; failures include `reason:"timeout"` or
   `reason:"rejected"`. On ok the relay mints `agent_token` and returns it to the waiting
   request: `{agent_token, device_id}`. Device rotates `link_code` and reports the new code
   on the same connection. Successful `pair.result` also carries the new `link_code`,
   allowing the relay to replace the old code within its approval transaction.

## Device ↔ relay wire (WS/WSS `/v1/device?id=<device_id>`)

First frame from device: `{"t":"hello","id":"molty-k7m2w9c4ya","key":"<b64 device_key>","fw":"...","caps":["fluid","say","listen","show","mood","creature"],"board":"waveshare-esp32-s3-touch-lcd-1.46","link_code":"..."}`
→ relay answers `{"t":"welcome"}` or closes with 4401.

`board` names the hardware (`firmware/boards/`, see [PORTING.md](PORTING.md)). `caps`
lists `say` / `listen` only when the board has a speaker / microphone; the relay answers
those commands `409 unsupported` up front, without calling TTS, when the device left them
out. The device itself answers a command its board cannot do with `error:"unsupported"`
(an unknown command is `unknown_command`).

Configure a relay origin (`wss://host` or `ws://LAN-IP:8787` for `wrangler dev`);
the device appends `/v1/device?id=<device_id>`. WSS verifies certificates/hostnames.
Close codes: **4400** malformed, **4401** bad key, **4409** replaced by a newer socket,
**4410** forgotten. A 4401 retries every 5 minutes and sets `auth_failed:true` in local
`GET /api/link` until welcome or local reconfiguration. Other disconnects use 1–60 s
backoff. Local status also includes `close_code` for the current/last attempt.

Text frames are JSON:
- relay→device `{"t":"cmd","id":"c17","name":"show","args":{...}}`
- device→relay `{"t":"res","id":"c17","ok":true,"result":{...}}` or `{"ok":false,"error":"code"}`
- device→relay `{"t":"evt","name":"shake|tap|button|say.done|link_code|...","data":{...}}`;
  `shake`/`tap`/`button` reach agents (see [Device events](#device-events) and [Events](#events-device--agents)), the rest is relay-internal.
- `pair.request` / `pair.result` as above; `{"t":"ping"}`/`{"t":"pong"}` every 20 s.
- device→relay on each rotation: `{"t":"link_code","code":"...","link_code":"..."}`.
  `code` is the requested spelling; `link_code` is a compatibility alias required by
  the built relay's current `room.ts` handler. Rotation does not reconnect the socket.
- device→relay `{"t":"forget"}`; relay revokes its room's bindings/tokens/jobs, sends
  `{"t":"forgotten"}`, then closes 4410. Local POST `/api/link/forget` returns 202 pending
  while the device performs this bounded exchange before erasing its identity.

Binary frames carry audio: `<JSON header>\n<payload>` (header ≤ 512 B, payload ≤ 16 KB).
Header: `{"s":"<stream id>","seq":N,"kind":"pcm16","rate":16000,"end":bool}`.
- Stream IDs allow 1–128 characters; omitted `end` means false. Header-only binary
  frames (without a newline/payload) are accepted. PCM payloads contain whole int16 samples.
  Text-frame limit is 64 KiB, independently of the audio-frame limit.
- `say`: relay sends `cmd say {job,text,ms,rate:16000,voice?}`; device starts `speaking`
  and text immediately, then acknowledges. Relay sends 320 ms PCM frames (`s` = job id),
  with three lead frames and paced delivery thereafter. After the last frame leaves
  the ring **and I2S DMA**, device returns to idle and sends
  `{"t":"evt","name":"say.done","data":{"job":"..."}}`. Failed/cancelled playback
  does not emit successful completion. Reader timing remains approximate (no word timestamps).
- `listen`: device streams mic PCM up; relay runs STT on `end`.

Moods (`mood` cmd, and the implicit `listening`/`speaking` around audio jobs) are moods
of the fluid creature's loaded `.molty` creature: the device applies
`{"state":"creature","mood":"<mood>"[,"hold_s":N]}` (blob when no creature is loaded).
During `say` the text state wins over the creature view.

What the screen does between commands (`firmware/main/fluid/fluid_director.h`):

- **The creature is home.** The device boots into it, and re-sending the state or mood it
  already shows changes nothing: a mood blends inside the creature instead of melting it
  and re-forming. The demo reel runs only on an explicit `state:"autoplay"` (never
  saved; pairing and the Improv "hi" go back to the creature, not the reel).
- **Quick moods revert.** `happy` (3 s) and `surprised` (2 s) return to `idle` on their
  own; `listening`, `thinking`, `speaking`, `sleepy` persist until the next mood.
  `hold_s` overrides either (`0` = until the next mood).
- **`show` returns** to the creature 1.5 s after its last word; `say` ends in `idle`.
- **Idle life.** While idle, the creature blinks, glances and breathes, and every
  20–60 s flashes a short `happy` or `surprised`. After 5 minutes without a touch or a
  command it dozes off (`sleepy`, 20 fps); a touch, a button, a shake or any command
  wakes it. `status` reports the mood on screen.
- **Status mark.** No Wi-Fi (a short arc), relay offline (a dim dot) or a refused device
  key (an accent dot) shows as a small mark at the bottom edge after 10 s; it never
  changes the state. Only the pairing code takes over the screen.

## Commands (v0)

| name | args | result | notes |
|---|---|---|---|
| `status` | — | fw, uptime, creature, state, mood, fps, rssi | relay adds `relay` {online, board, caps, ...} |
| `state` | `{state, ...}` | creature state JSON | passthrough to `/api/creature/state` semantics |
| `mood` | `{mood, hold_s?}` | — | idle listening thinking speaking happy sleepy surprised; `hold_s` 0..3600 (0 = until the next mood; default: happy/surprised revert, the rest persist) |
| `show` | `{text, wpm?}` | — | speed reader in the fluid; back to the creature 1.5 s after the last word |
| `say` | `{text, voice?}` | `{job}` immediately | relay does TTS + streams; device sets `speaking`, shows text in sync. `unsupported` without a speaker |
| `listen` | `{ms≤10000}` | `{job}` immediately | device sets `listening`, streams mic; relay STT → job result `{text}`. `unsupported` without a mic |
| `volume` | `{volume 0..21}` | — | `unsupported` without a speaker |
| `imu` | — | snapshot | `unsupported` without an IMU |
| `diag` | `{timeline? 0..180}` | `/api/diag` JSON | frame histograms, task CPU %, heap, stalls, net; `timeline` = seconds of 1 Hz rows |
| `log` | `{since?, max? 1024..32768}` | `{next, text}` | device log ring tail (ESP_LOG + `EVT` lines); pass `next` back as `since` |
| `creature.file` | (later) | — | upload `.molty` via relay |

Agent-facing calls are **async-friendly** (agent runtimes commonly cap a tool call at ~10 s / 64 KiB):
`say`/`listen` return a `job` id; `molty_wait {job, timeout_s≤8}` returns the result or
`pending`. Short calls answer inline.

## Device events

Device→relay `{"t":"evt","name":...,"data":{...}}` frames, sent only while the link is up
(not queued) and never while a pairing is pending (its tap and buttons decide the
pairing). Rate-limited on the device. `shake`, `tap` and `button` reach agents through the relay's inbox ([Events](#events-device--agents)).

| name | data | when |
|---|---|---|
| `say.done` | `{job}` | a `say` finished playing (its last PCM left the speaker) |
| `shake` | `{peak_g, reversals, ms}` | the board was shaken (boards with an IMU): ≥ 3 sign reversals of > 1.2 g dynamic acceleration on one axis within 800 ms; ≤ 1 per 2 s. `peak_g` largest dynamic acceleration (g), `ms` first peak → detection |
| `tap` | `{x, y}` | a finger touched the screen (boards with touch); 0..1 of the panel from the top left; ≤ 4/s |
| `button` | `{id: "accept"\|"reject"}` | a button was pressed (the board's accept / reject buttons); ≤ 4/s |

The device reacts to a shake by itself (a brief `surprised`), agent or not. Detector
constants: `firmware/main/sense/gesture.h`.

## Agent surfaces

- **Remote MCP** `https://<relay>/mcp` (streamable HTTP), `Authorization: Bearer <agent_token>`.
  Tools: `molty_pair`, `molty_status`, `molty_mood`, `molty_show`, `molty_say`, `molty_listen`,
  `molty_wait`, `molty_state`, `molty_volume`, `molty_imu`, `molty_diag`, `molty_log`, plus the
  relay-only `molty_events` and `molty_webhook` ([Events](#events-device--agents)). Shared names
  have the same semantics as the local stdio MCP in `cli/`.
- **REST** `POST /v1/devices/<id>/cmd {name,args}`, `GET /v1/jobs/<job>`,
  `GET /v1/devices/<id>/events`, `GET|PUT|DELETE /v1/webhook`, same bearer.
- **Skill page** `GET /skill.md` (and `/skill`), no auth: the agent's self-setup guide (see
  Pairing flow step 1). Kept in sync with `commands.ts`/MCP tools by `test/skill.test.ts`.
- **CLI** `molty --relay <url> --token <t> ...`, or `molty pair` once and the saved link (see [CLI.md](CLI.md)).

## REST envelopes

Agreed between the relay (`relay/`) and the Go CLI relay transport. The
bearer is `agent_token` = `<device_id>.<base64url(32 bytes)>`; the prefix only routes.

| Call | Success | Failure |
|---|---|---|
| `POST /v1/pair {device_id, link_code, agent_name}` (no token; long-polls ≤ 120 s) | `200 {ok:true, agent_token, device_id, agent_name, code}` | `{ok:false, error}`: `bad_link_code` 403, `rejected` 403, `timeout` 408, `device_offline` / `pair_busy` 409 |
| same with `wait_s` < 120, or `{device_id, pair_id}` to resume | `202 {ok:true, status:"pending", pair_id, code, expires_in_s}` while undecided | as above |
| `POST /v1/devices/<id>/cmd {name, args}` | `200 {ok:true, result:{...}}`; `say`/`listen` → `{ok:true, result:{job}}` | `{ok:false, error:"code"}`: 401 bad/missing bearer, 400 `invalid_args`/`unknown_command`, 409 `device_offline`/`audio_busy`/`unsupported`, 504 `device_timeout`, 502 device-reported codes |
| `GET /v1/jobs/<job>[?wait_s=0..8]` | `200 {job, kind, status:"queued"\|"running"\|"done"\|"failed", result?, error?}`; say done `{ms, text}`, listen done `{text, duration_ms, peak, rms}` | 401, 404 `not_found` |
| `DELETE /v1/token` | `200 {ok:true, result:{revoked:true}}` | 401 |
| `GET /v1/devices/<id>/events[?since=e41&wait_s=0..25]` | `200 {ok:true, events:[{id,type,ts,data}], next, more}` | 401, 400 `invalid_args` |
| `PUT /v1/webhook {url, method?, headers?, body?, content_type?}` | `200 {ok:true, result:{webhook, secret, secret_note, dry_run}}` | 401, 400 `invalid_args` (with the reason) |
| `GET` / `DELETE /v1/webhook` | `200 {ok:true, result:{webhook\|null}}` / `{removed}` | 401 |

Any authenticated response may also carry the caller's unread events as a top-level
`events` array (+ `more_events:true`): additive, absent when there are none.

Device-local console API (same Wi-Fi, no auth; served by the firmware, used by
`console/`). One spelling per field — `relay_url` is the ws/wss origin the
device dials; agents/CLI use its http(s) twin (`ws://h` → `http://h`, `wss://h` → `https://h`).

| Call | Success | Failure |
|---|---|---|
| `GET /api/link` | `200 {device_id, link_code, relay_url, pair, last_pair, connected, auth_failed, close_code}` | `500` link unavailable |
| `POST /api/link {relay_url}` (any Content-Type) | same body as GET; saved to NVS, reconnects | `400` not a `ws://`/`wss://` origin |
| `POST /api/link/forget` | `202 {ok:true, pending:true}` | `500` |

`pair`: `null`, or `{agent_name, code, expires_in_s}` for a request currently awaiting the
tap. `last_pair`: `null` until the first decision since boot (RAM only), then
`{seq, agent_name, ok, reason}` for the most recent `pair.result` the device sent; `seq`
increments per decision; `reason` is `null` when `ok`, else `"rejected"` or `"timeout"`
(immediate rejections — e.g. while audio is busy — count too). A pending request dropped by
a relay disconnect clears `pair` without a decision. Example while pending, then after:
```
{"device_id":"molty-k7m2w9c4ya","link_code":"K7M2W9C4","relay_url":"wss://relay.example","pair":{"agent_name":"Claude Code","code":"4821","expires_in_s":97},"last_pair":null,"connected":true,"auth_failed":false,"close_code":0}
{"device_id":"molty-k7m2w9c4ya","link_code":"Q3XH8ND2","relay_url":"wss://relay.example","pair":null,"last_pair":{"seq":1,"agent_name":"Claude Code","ok":true,"reason":null},"connected":true,"auth_failed":false,"close_code":0}
```

`state` cmd: empty args = read; `{state:{...}}` or flat fields = patch (sent to the
device flat). MCP `molty_wait` maps job status to `pending` (queued/running), the job
result plus `status:"done"`, or a tool error for `failed`.

## Events (device → agents)

Molty is not only driven; it reports what its human does to it. Agent-visible events
travel device → relay → each paired agent's own inbox → the agent, by whichever receive
mode suits that agent.

```
device evt ──WSS──▶ DeviceRoom.onEvt
                     ├─ allow-list + shape check (shake, tap, button; rest stays internal)
                     ├─ cap 30/min/device (excess dropped, counted)
                     └─ ev:<seq> ring (200 / 24 h, DO storage)
                          │  one read cursor per agent token (cur:<token hash>)
                          ├─▶ ride-along: unread `events` on every authenticated response
                          ├─▶ pull: GET /v1/devices/<id>/events · molty_events (long-poll)
                          │      └─▶ `molty events [--exec cmd]` (CLI, JSON lines)
                          └─▶ webhook: whq:<token hash>:<seq> ─DO alarm─▶ agent-defined HTTPS request
```

### Firmware contract

`{"t":"evt","name":<type>,"data":{…}}`. Only these reach agents; anything else (`say.done`,
`link_code`, …) is relay-internal. An event whose data does not match is dropped.

| type | data |
|---|---|
| `shake` | `{peak_g: number 0..64, reversals: int, ms: int}` |
| `tap` | `{x: 0..1, y: 0..1}` (screen position, unit square) |
| `button` | `{id: "accept" \| "reject"}` |

The relay stores `{id:"e<seq>", type, ts:<relay unix ms>, data}`; `seq` increases per device.

### Inbox and cursor

- Ring: the last **200** events, none older than **24 h** (trimmed on append, also in DO
  storage so it survives hibernation and eviction).
- Intake cap: **30 events/min per device**; the excess is dropped (counted in storage).
- Each agent token has a cursor. A newly paired agent starts at the head (no backlog).
  Every way of reading below advances only that agent's cursor, so two agents each get
  every event once. Webhook deliveries that succeed also count as read.
- Ids are stable: an agent using two modes at once may see an event twice; dedupe by `id`.

### Receive modes

| Mode | Call | Notes |
|---|---|---|
| Ride-along | any authenticated REST response / MCP tool result | REST: additive top-level `events` (+ `more_events`). MCP: `events` in `structuredContent` and a second text item `Molty: was shaken (peak 2.4 g) 2 min ago [e42].` At most 10 per response; no unread events = the response is unchanged |
| Pull | `GET /v1/devices/<id>/events[?since=e41][&wait_s=0..25]` · MCP `molty_events {since?, wait_s? 0..8}` | `{ok:true, events:[…], next:"e42", more}`, oldest first, ≤ 50. Default `since` = cursor; long-poll returns as soon as an event lands. An explicit `since` never moves the cursor backwards |
| Webhook | `PUT /v1/webhook` · `GET` · `DELETE` · MCP `molty_webhook` | per-agent HTTPS request, see below |
| Stream | `molty events [--n N] [--exec CMD]` | CLI loop over the pull call ([CLI.md](CLI.md#events-and-receiving)) |

Nothing can wake an agent that has neither a reachable endpoint nor a running process; such
an agent sees events the next time it calls anything (ride-along).

### Webhooks

`PUT /v1/webhook` (or `molty_webhook`), body:

```
{"url": "https://…", "method"?: "POST"|"GET"|"PUT"|"PATCH",
 "headers"?: {"Authorization": "Bearer …"}, "body"?: "<template>", "content_type"?: "application/json"}
```

- Placeholders in `url` (URL-encoded) and `body`: `{{event.type}}` `{{event.id}}` `{{event.ts}}`
  `{{event.data}}` (JSON) `{{event.data.<field>}}` `{{device}}` `{{text}}` (a short sentence:
  "Molty was shaken (peak 2.4 g)", "Molty's screen was tapped", "Molty's accept button was
  pressed"). With a JSON `content_type` strings are JSON-escaped (write them inside quotes;
  write `{{event.data}}` and numeric fields unquoted); with
  `application/x-www-form-urlencoded` they are form-encoded; otherwise inserted raw.
  Unknown placeholders are rejected; missing fields render empty.
- No `body`: the relay's own `{"device":"molty-…","event":{id,type,ts,data}}`, `application/json`.
- Every request carries `Molty-Signature: t=<unix ms>,v1=<hex hmac_sha256(secret, t + "." + body)>`
  (GET: empty body). Harmless for targets that ignore it.
- Registration validates and **dry-runs** the template on a sample `shake` and returns
  `{webhook, secret, dry_run}`. `secret` is shown once (re-registering rotates it and
  re-enables a disabled webhook). Header values, the secret and the URL path/query (often a
  bot token) are never echoed again: `status`/`GET` show `{url: origin + "/…", method,
  headers: [names], active, consecutive_failures, disabled?, last_ok_at?, last_error?}`,
  as `relay.webhook` in `status` too. Logs carry the origin only. The dry run echoes the
  rendered body, so keep secrets in headers or the URL.
- Limits: url ≤ 2048 B, body template ≤ 4096 B, ≤ 16 headers / 4096 B; reserved headers
  (`Host`, `Content-Length`, `Molty-Signature`, …) refused; `Content-Type` comes from `content_type`.
- Delivery: queued in DO storage, sent from the DO alarm, 5 s timeout, redirects not
  followed (a 3xx is a failure), 2xx = success. Retries after 1 s, 10 s, 60 s, then the event is
  dropped for that agent. **20 consecutive failed attempts disable the webhook.**
- SSRF guard: `https:` only; no credentials in the URL; no IP literals (v4, v6, hex/decimal
  forms); no `localhost`, single-label names or `.local`/`.localhost`/`.internal`/`.lan`/
  `.home`/`.home.arpa`/`.corp`/`.intranet`/`.localdomain`. The rendered host is resolved
  (A + AAAA over DNS-over-HTTPS on Workers) at registration and before every delivery and
  refused if any address is private, loopback, link-local, CGNAT, multicast, documentation
  or otherwise reserved. **Residual risk, stated plainly:** Workers' `fetch` resolves the
  name again itself, so a DNS-rebinding host could answer differently between our check
  and the request (TOCTOU), and the check trusts the DoH answer. What bounds it: Workers
  egress comes from Cloudflare's network, not from the owner's LAN, so private addresses
  of the owner's home are not reachable from the relay at all; the guard mainly stops
  pointing the relay at Cloudflare-internal or other tenants' private-looking endpoints.

#### Reference verifiers

Use the raw request body exactly as received. Reject when the header is missing, the
signature differs, or `t` is older than your tolerance (replay).

<!-- verifier:ts -->
```ts
// Node 20+, Deno, Bun, Workers (Web Crypto). True when the request is authentic and fresh.
export async function verifyMolty(secret: string, header: string | null, body: string, toleranceMs = 5 * 60 * 1000): Promise<boolean> {
  const m = /^t=(\d+),v1=([0-9a-f]{64})$/.exec(header ?? "");
  if (!m || Math.abs(Date.now() - Number(m[1])) > toleranceMs) return false;
  const enc = new TextEncoder();
  const key = await crypto.subtle.importKey("raw", enc.encode(secret), { name: "HMAC", hash: "SHA-256" }, false, ["verify"]);
  const sig = new Uint8Array(m[2].match(/../g)!.map((h) => parseInt(h, 16)));
  return crypto.subtle.verify("HMAC", key, sig, enc.encode(`${m[1]}.${body}`)); // constant-time
}
```

```python
import hashlib, hmac, time

def verify_molty(secret: str, header: str | None, body: bytes, tolerance_s: int = 300) -> bool:
    """True when the request is authentic and fresh. body = raw request bytes."""
    try:
        parts = dict(p.split("=", 1) for p in (header or "").split(","))
        t, v1 = parts["t"], parts["v1"]
    except (ValueError, KeyError):
        return False
    if not t.isdigit() or abs(time.time() * 1000 - int(t)) > tolerance_s * 1000:
        return False
    mac = hmac.new(secret.encode(), t.encode() + b"." + body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(mac, v1)
```

### Example setups by agent kind

These are examples, not rules; skill.md deliberately lets each agent choose.

- **Shell-capable, long-running (Claude Code, Codex CLI, local OpenClaw).** Run the CLI as
  a background process and treat each output line as a wake-up.
  - Claude Code: start `molty events` with the Bash tool's `run_in_background`, then watch
    it with the Monitor tool (or read its output file between turns); each JSON line is one
    event. Example: `molty events --exec 'cat >> ~/.molty-events.jsonl'`.
  - Codex CLI / local OpenClaw: launch `molty events --exec '<your wake hook>'` as a
    long-lived child (or a `systemd --user` / `launchd` service) whose `--exec` command
    posts to the agent's local wake endpoint or appends to the file it watches.
- **Server-hosted (bots on xAI/OpenAI/Anthropic APIs, cloud OpenClaw).** Register a
  webhook pointing at the bot's own HTTPS endpoint (default body, verify the signature), or
  directly at the platform's message/run API with a template.
- **Chat apps (ChatGPT, claude.ai, Claude Cowork, grok.com).** No endpoint, not running
  between turns: rely on ride-along, and call `molty_events` at the start of a turn when
  the human is talking about Molty. Do not claim to react live.

## Default relay

Each component has exactly one default relay URL, all set to the same value
(`molty-relay.alicenet.workers.dev`, the project's hosted relay). Change it in these
three places to point a build at your own relay (see `relay/README.md` to deploy one):

| Component | Where | Used when |
|---|---|---|
| firmware | `CONFIG_MOLTY_DEFAULT_RELAY` in `firmware/main/Kconfig.projbuild` (`wss://…`) | no relay URL saved in NVS (`POST /api/link {relay_url}` overrides) |
| console | `DEFAULT_RELAY` in `console/src/ui/agent-link.ts` (`https://…`) | the device has not reported a `relay_url` yet |
| CLI | `DefaultRelay` in `cli/internal/molty/link.go` (`https://…`) | `molty pair` without `--relay` / `MOLTY_RELAY` |

The website's waitlist form posts to the same hosted relay (`WAITLIST_URL` in
`website/src/config/site.mjs`, `POST /waitlist`, relay/README.md "Waitlist"); it is not part
of the agent link.
