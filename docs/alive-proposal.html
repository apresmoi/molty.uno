Molty Alive Layers

Design proposal, nothing built. 2026-11-22. How a Molty file says how it breathes, looks around, listens, thinks and talks.

Recommendation

Give every Molty an optional life block with three parts. Signals are named numbers that move: breathing, blinks, where it looks, how loud it speaks. Layers are small clips added over today's mood loop, each moved and weighted by a signal. Moments fire whole gestures when a signal says so. Mood stays the one word the agent sends; inside the Molty it becomes signal values, so sleepy slows the breath. A Molty without the block plays exactly as today. Start with breathing, blinks and glances on the cat, scored by a rig.

Key choices

  • A signal is a named number. A few come from the device (voice, touch, time); the Molty defines the rest.
  • Signals read other signals: mood sets energy, energy sets breathing speed.
  • A layer is a small clip added over the mood loop; a signal moves it and sets its strength.
  • Moments fire gestures (a glance, a nod, a yawn) on random gaps or on a reaction, never on a fixed clock.
  • Mood stays the agent's one word; the Molty turns it into signal values.
  • The device runs it on the signal engine the duck already uses: about 1 ms of a 33 ms frame.
  • Today's cat and files play exactly as now; the idle and listening habits in C become the fallback.
  • A rig plays any Molty through the real firmware and scores repeats, stillness, lip sync and delay.

Open decisions

  1. Agents keep sending only moods, never raw signals? I say yes.
  2. Authors write a readable life block, not the duck's raw formula language? I say yes.
  3. The cat's idle, thinking and listening habits move from C into its file? I say yes.
  4. The preview runs the real firmware, so layers are written once, not twice? I say yes.
  5. The mouth follows the sound the device plays, not mouth shapes sent by the relay? I say yes.
1. What is hardcoded today and why the cat looks looped

The cat is played one clip at a time: its mood loop, or a gesture, or the walk between two poses, crossfaded. Everything that makes it look alive is either baked into those clips or decided in C. Five things stand out.

WhatWhere it lives todayWhat it does to the cat
Every mood loop is exactly 4.0 sthe cat's clipsIdle, listening, thinking, speaking, happy and sleepy each repeat the same 4 s forever. The eye catches the beat in under a minute. This is most of the "dead" feeling.

It is fast (worst frame 0.2 ms on the device's chip) and has matching JavaScript and C players. The cat skipped it because it is a baked rig. This design gives the rig that engine back.

3. The model: signals, layers, moments and how they compose

Three words

  • Signal: a named number, worked out every frame. It can be steady (energy 0.6), moving (a breath going -1 to 1), or a short pulse (a blink, 0 to 1 and back in a quarter second). A trigger is a signal that is a pulse.
  • Layer: one thing added on top of the base pose. Either a clip from the body file (a breath, a blink, a look to the side) whose position is set by a signal, or a direct turn of some bones by a signal. It has a strength (a signal too), a mode (add, or replace for bones it owns while it is on) and the bones it may touch.
  • Moment: a gesture (a whole clip on the base track, like nod or yawn) started when a trigger fires. This is how the idle library and listening reactions become data.

The base track is today's clip player, unchanged: the mood loop, the agent's gestures, the walks between poses. Layers ride on it. Moments ask it to play a gesture, the same way the agent does.

Where signals come from

FromSignalsKind

The device list is the only fixed vocabulary. It is small on purpose, it names facts about the world (never "how a cat breathes"), and it only grows.

Signal kinds (what an author can make)

Each kind is one key. Any number in it may instead be a signal's name or a mood table (below).

KindMakesExample
mooda value per mood, blended by the mood weights{ "mood": { "_": 0.5, "sleepy": 0.1 } }
from + mapanother signal, reshaped by a few points{ "from": "energy", "map": [[0, 0.16], [1, 0.42]] }
sumsignals added, each with an amount{ "sum": [["energy", 1], ["tired", -0.3]] }
wavea smooth -1 to 1 swing at a rate (per second); each cycle a little faster or slower{ "wave": "breath_rate", "vary": 0.15, "rise": 0.4 }
noisea smooth wander, -1 to 1{ "noise": 0.15 }
holdpicks a value, holds it a random time, moves to the next quickly: the way eyes and ears move{ "hold": [0.6, 3], "range": [-1, 1], "move": 0.12 }
everya pulse after a random gap: a trigger with a shape{ "every": [3, 7], "lasts": 0.25, "double": 0.12 }

peaksa trigger on each peak of a level: syllables in speech{ "peaks": "voice_out", "above": 0.3, "gap": 0.18 }
followanother signal, late and springy: overlap and follow-through{ "follow": "look_x", "lag": 0.25, "bounce": 0.2 }

Options any kind takes: ease (seconds to settle; two numbers for up and down, which is how a mouth opens fast and closes slower), when (a signal that gates it, eased, so "when": "thinking" fades it in only while thinking), range, scale.

How a signal feeds another

By name. breath_rate reads energy, breath reads breath_rate, the breathing layer reads breath. The build tool sorts them so each is worked out after what it reads, and refuses a loop (unless it goes through a follow, which uses last frame's value). The device never sorts anything; it runs them in the order the build wrote.

Mood feeds energy, the idle time feeds tiredness, and both set the breathing speed: the cat breathes faster when happy, slower when sleepy, and slows down a little more the longer nobody talks to it. Mood also sets the blink gaps (quicker while listening).

4. Mood: a state outside, signal values inside the decision

Three ways to see mood, and the pick:

not this Mood is just a signal. Agents could send energy 0.3 or any number. Flexible, but every agent must learn every Molty's numbers, and two Moltys would disagree on what "energy" means. The skill gets harder for nothing the human sees.

not this Mood stays a built-in state. As today: seven names, each a loop, rules in C. Simple, but nothing can read it smoothly, so breathing cannot know how sleepy it is.

pick Mood is a state the agent picks, and inside the Molty it is a set of signal values. The agent's side does not change: one of idle listening thinking speaking happy sleepy surprised, or working, plus gestures, sent as today or as inline marks like [happy]. The device turns the current mood into eased weights (mood_happy rising from 0 to 1 over about a second while the old one falls). Any number in the file can be a mood table, so "sleepy breathes slower" is one line. The base track still plays each mood's loop, so a Molty with no life block behaves as today.

A mood table is written { "_": 0.5, "sleepy": 0.1, "happy": 0.9 }: _ for every mood not named. It is worked out as the sum of each mood's value times its weight, so a mood change slides every value instead of jumping.

The device itself still sets two moods, as today: sleepy after 5 quiet minutes, surprised on a shake. Those are device rules about the person (are they here?), not about how a cat moves, so they stay in C. What the cat does when it gets sleepy is the file's.

5. The file: what the cat's author writes and the same idea on a tiny Molty

The block goes in molty.json next to moods and gestures. The clips it names (breath, blink_pose, look_lr ...) are ordinary actions in the body file: the author makes them in Blender like any other. A pose clip is short: its first key is neutral, its last key is the full effect (a full breath in, eyes shut, mouth wide). A signal slides through it.

moltys/cat/molty.json: the additions (cat 2.1.0)

"life": {
  "signals": {
    // how lively it is: from the mood, and slower the longer it is left alone
    "energy":      { "mood": { "_": 0.45, "listening": 0.7, "speaking": 0.7, "happy": 0.9, "sleepy": 0.1, "surprised": 1 } },
    "tired":       { "from": "idle_time", "map": [[60, 0], [300, 1]] },
    "calm":        { "sum": [["energy", 1], ["tired", -0.3]] },

    // breathing: never the same length twice, in a little faster than out
    "breath_rate": { "from": "calm", "map": [[0, 0.16], [1, 0.42]] },
    "breath":      { "wave": "breath_rate", "vary": 0.15, "rise": 0.4 },

    // blinks: random gaps, quicker when engaged, now and then a double
    "blink":       { "every": { "_": [3, 7], "listening": [2, 4], "speaking": [2, 4], "sleepy": [8, 14] },
                     "lasts": 0.25, "double": 0.12 },

    // where it looks: a glance, a hold, back to you; thinking looks up and aside
    "look_x":      { "hold": [0.6, 3.0], "range": [-1, 1], "move": 0.12, "home": 0.4 },
    "look_y":      { "hold": [0.8, 3.5], "range": { "_": [-0.3, 0.3], "thinking": [0.2, 0.9] }, "move": 0.15 },
    "head_x":      { "follow": "look_x", "lag": 0.25, "bounce": 0.2 },

    // ears swivel on their own; prick toward a voice
    "ears":        { "hold": [1, 6], "range": [-1, 1], "move": 0.08 },
    "ears_voice":  { "from": "voice_in", "map": [[0.05, 0], [0.5, 1]], "ease": 0.3 },

    // the tail wanders; faster when happy, slow when thinking
    "tail":        { "noise": { "_": 0.15, "happy": 0.5, "thinking": 0.08 } },

    // it shifts its weight every so often
    "shift":       { "hold": [8, 25], "range": [-1, 1], "move": 1.2 },

    // talking: the mouth follows its own voice, the chin lifts on strong syllables
    "jaw":         { "from": "voice_out", "ease": [0.03, 0.09] },
    "syllable":    { "peaks": "voice_out", "above": 0.35, "gap": 0.25 },
    "lift":        { "on": "syllable", "lasts": 0.35 },

    // a touch: it looks up at you a beat later
    "noticed":     { "on": "touch", "delay": [0.15, 0.35], "lasts": 1.2, "rest": 2 },

    // the beats that start small things and gestures
    "ponder":      { "every": [2, 5], "when": "thinking" },
    "idle_beat":   { "every": [10, 40], "rate": "life", "when": "free" }
  },

  "layers": [
    { "layer": "breathing", "clip": "breath",     "by": "breath" },
    { "layer": "blink",     "clip": "blink_pose", "by": "blink",  "bones": ["eye.L", "eye.R"] },
    { "layer": "gaze",      "clip": "look_lr",    "by": "head_x", "zero": 0.5, "weight": "free" },
    { "layer": "gaze_up",   "clip": "look_ud",    "by": "look_y", "zero": 0.5, "weight": "free" },
    { "layer": "noticed",   "clip": "look_ud",    "by": "noticed", "zero": 0.5 },
    { "layer": "ears",      "clip": "ears_turn",  "by": "ears",   "zero": 0.5, "bones": ["ear.L", "ear.R"] },
    { "layer": "ears_prick","clip": "ears_prick", "by": "ears_voice" },
    { "layer": "tail",      "turn": { "bones": "tail6-tail12", "y": ["tail", 12], "ripple": 0.06 } },
    { "layer": "weight",    "clip": "shift",      "by": "shift",  "zero": 0.5, "weight": { "_": 1, "sleepy": 0 } },
    { "layer": "mouth",     "clip": "mouth_open", "by": "jaw",    "mode": "replace",
                            "bones": ["mouth", "tongue"], "weight": "talking" },
    { "layer": "chin",      "clip": "chin_lift",  "by": "lift" },
    { "layer": "pondering", "once": { "ear_flick": 3, "tail_swish": 3, "head_tilt": 2, "slow_blink": 1 },
                            "on": "ponder", "weight": "free" }
  ],

  "moments": [
    { "on": "idle_beat",      "pick": { "glance_left": 3, "glance_right": 3, "look_up": 2, "stretch": 1.5, "wobble": 1.5 } },
    { "on": "heard_pause",    "play": "nod",  "delay": [0.15, 0.35], "rest": 2.5 },
    { "on": "heard_question", "play": "glance_left" },
    { "on": "said_end",       "play": "happy", "chance": 0.3, "rest": 60 }
  ]
}

What each field means

FieldMeaning
clip + byThe clip's position comes from the signal: 0 is the clip's start, 1 its end. Values below 0 or above 1 are clamped.
zeroWhere in the clip the neutral pose is (default 0). 0.5 for a clip that goes left, neutral, right, so a signal from -1 to 1 maps across it.
clip + loopInstead of by: the clip plays on its own clock, with speed (a number, a signal or a mood table) and a random start.
once + onInstead of by: when the trigger fires, one clip is picked by weight (never the same twice in a row) and played once over the base.
turnNo clip: these bones turn by signal times degrees. ripple delays each bone down the chain by that many seconds, which is follow-through without authoring it.
modeadd (default): the difference from the neutral frame is added, so it works on any pose. replace: on its bones, it takes over by its weight (the mouth while talking, so the baked speaking loop's mouth gives way to the real voice).
bonesThe bones it may touch (default: all the clip moves). A range like tail6-tail12 is a chain.
weightStrength 0 to 1: a number, a signal or a mood table. Eased, so layers fade in and out. free fades the glances while a gesture plays so they never fight.
moments: play or pickA gesture on the base track, routed as today. delay, chance, rest (the least seconds between two).

Layers apply in file order. Moments obey the owner's setting: with idle life off, no moment starts on its own (only reactions to the human, and only when the setting allows them today).

6. What makes it feel alive each idea, and how the file says it

The four that give most of the life

  1. Breathing that is not the loop's length. A breath of 2.4 to 6 s, varying each cycle, over a 4 s loop: the two never line up the same way twice, so the 4 s beat disappears. One signal, one tiny clip.
  2. Blinks on random gaps, sometimes double. The strongest "someone is in there" cue in every character tool (Live2D ships it built in). One signal, one tiny clip.
  3. Look, hold, look back. Eyes and head jump to a spot, stay a random while, return. Real eyes do this; smooth drifting looks robotic. One hold, one clip, and the head follows the eyes a quarter second late.
  4. The mouth follows the real voice. When it speaks, people watch the mouth first. One device signal, one clip.

Those four are the first slice. Ear life, tail ripple and weight shifts come next; reactions and thinking habits after.

The budget

A frame is 33.3 ms at 30 frames a second. Today the cat's play and dots take about 8 to 13 ms sitting or standing and 17 to 18 ms walking side on (measured on the computer and scaled to the device; the docs ask for a confirmation on the device). The water sim under the cat is held still. Life gets 1 ms, a hard line the rig and the device's own frame profile check.

8. Compatibility no flag day
  • No life block: the same pixels. The fidelity script (the firmware and the web build play the same steps and must show the same pixels) is the oracle. Today's cat 2.0.0 gives the same hash on every frame before and after the firmware learns layers.
  • The C habits stay, as the fallback. The idle library, the work library and the listening reactions keep running for any Molty that does not list moments. A Molty that does list them takes over, the way the duck already takes over working (the director already has that switch for work; idle and listening get the same switch).
  • The duck and the octopus do not change. They keep their own formula layers.
  • The agent's side does not change. Same moods, same gestures, same inline marks. The skill needs no update.
  • Older firmware refuses unknown keys in a Molty file ("creature: unknown key"), so a 2.1 cat cannot install on it. That is the safe failure, but it must be said plainly: the device reports a life capability, the install flow and the check say "needs a newer Molty" instead of a parse error, and the built-in cat moves to 2.1.0 in the same firmware that learns layers.
  • Order: firmware learns signals and layers (cat unchanged, hashes unchanged), then cat 2.1.0 ships its life block, then the C habits move into the cat's file one at a time, each checked by the rig before and after.
9. The rig: measuring "alive" what a script judges, what a person judges

We already have the pieces. The real firmware's drawing code runs as a web module under Node, driven by a step script (frames, touch, shake, mood, listen with a level, say), and it can hand back the creature's dots alone, without the dust. The rig is a small Node script on top: same Molty file, same steps, a fixed seed, and it writes pictures and numbers.

What a person judges

  • Blind side by side. Two glasses, before and after, same steps, sides shuffled: "which one is alive?" A change ships only if it wins.
  • Name the mood. A silent 10 s clip per mood: can Juan tell which it is? Target: 6 of 7.
  • Nothing weird. A contact sheet (a frame every half second on one page) per scene, for twitches, pops, stuck poses.
  • On the device, last. The final judge is the round glass on the desk, after the rig says it is in budget.

Scripts guard what is measurable and catch regressions; the person judges taste. Neither replaces the other.

The smallest rig worth building first: the 60 s idle scene on today's cat, three numbers (loop echo, still share, rhythm spread) and one contact sheet. It needs no firmware change and no new glue: it reuses the step player and the creature-only picture. It should show the 4 s loop plainly. That is the baseline every slice is scored against.

11. Competing designs where two really compete, and the pick

How authors write signals

pick A readable block, compiled. A few named kinds (wave, hold, every, follow ...), each one key. The build turns them into the duck's existing formula program, so the device keeps one engine that is already fast and already matched between JavaScript and C.

not this The raw formula language in the file. Already exists, can express anything. But [0.6, ["dz", "@t", 0.3, 7]] is not something a person writes or reviews, and it ties the public format to one engine's insides.

Where life lives: layers over clips, or a blend graph

pick A flat list of layers over the base track. Easy to read, easy to add to, easy to degrade: drop a layer and the rest still works. Today's player and its routes stay as they are.

not this A full blend graph (Unity, Godot): nodes wired into a tree. More power for crossfading many moods by numbers, but it would replace a player that works, and Molty's moods are few and discrete.

Small life: clips or code-like motion

pick Pose clips moved by signals, plus simple bone turns. The artist draws the breath in Blender and it looks like the cat; the signal only says when and how much. Turns cover the cheap cases (a tail sway, a blob's squash).

not this Everything as bone formulas, like the mood engine. No new clips, but every motion becomes a numbers puzzle and the cat stops looking like what was drawn.

12. Open decisions in full recommendation, and what changes otherwise
  1. Agents send only moods, never raw signals. I recommend yes: the skill stays as it is, and every Molty reads a mood its own way. If no: the agent API grows a feel command, Moltys must agree on shared signal names, and the skill must teach them.
  2. Authors write a readable life block, compiled to the existing engine. I recommend yes. If the raw formula language is exposed instead: more power on day one, but files nobody can read, and the public format tied to one engine.
  3. The cat's idle, thinking and listening habits move from C into its file. I recommend yes, with C kept as the fallback for Moltys without moments. If no: less firmware work, but "nothing per-Molty in C" is not met and every Molty idles like the cat.
  4. The preview runs the real firmware, so layers are written once. I recommend yes: the website's demo already runs it. If no: layers get written twice (the JavaScript reference player and C) and kept equal by tests, as the duck's engine is today, roughly doubling slices 1 to 3.
  5. The mouth follows the sound the device plays. I recommend yes: one loudness number, no relay change, no extra latency. If mouth shapes (visemes) come from the voice box instead: richer lips, but a new stream on the relay, more bytes, and timing to keep in step with the sound.
